# Ecosystem Audit

Self-contained weekly audit (cron `workflow-ecosystem-audit`, Mon 07:00). No user present — no questions. **Only writes allowed: patches to `decide/SKILL.md` + the sync scripts' own output.** Everything else is read-only; report findings.

**Interactive variant.** When a person asked for the audit, finish discovery first, then present a prioritized plan (P0-P3, with evidence and the exact change per item) and get approval before config or data edits. Read-only repairs (malformed frontmatter, a dead provider entry, a 0-tool MCP) can be fixed during discovery; anything touching user data, credentials, or a service window waits for the go-ahead.

## Steps

1. **MCP health** — `hermes mcp list` (run from anywhere; the live list is the source of truth). Then test each enabled server: `timeout 60 hermes mcp test <name>`. ⚠️ In a loop, `| tail -5` scrolls early results out of the process log buffer — run servers individually, or grep `✓|✗|Connected|failed|Unauthorized`.
   - **Expected failures, not regressions:** `opendesign` → connection failed when the Open Design app isn't running (daemon-gated; `od-*` skills are the fallback, documented in /decide). `figma` → `401 Unauthorized` = Composio auth expired, needs re-auth. Both are signatures, report as "expected/down", don't treat as breakage.
   - The enabled-server roster drifts between audits — don't hold a hardcoded baseline against it; flag servers that appeared or vanished vs the previous audit (report only). Resource-heavy servers (obsidian-kg-style) report "1 tool" in `hermes mcp test` but expose more via resources/prompts — a live `list_resources` call proves they work.
2. **Skills inventory** — `python3 ~/.hermes/scripts/skills_health.py` (exit 1 = unparseable frontmatter, empty description, duplicate name in one root, or plugin skill without a description; advisories list descriptions that clip on a stopword). Then `python scripts/audit-skills.py` in the repo for the published copy. Cross-check `external_dirs` in `config.yaml` exist. Baseline 2026-08-14: 412 skills / 33 categories / 19 external_dirs.
   - Profile drift (the daily `drift_check.py` compares each profile's `skills.external_dirs` + `mcp_servers` against global): `extra ... (stale in profile)` entries pointing at paths that don't exist on this host are safe to delete; `missing` entries are usually deliberate per-profile scoping — report them, don't force-add without asking. Deliberate exemptions must be encoded IN the checker (an explicit allowlist of offline/minimal profiles), not judged per run — a drift check that flags the same by-design gap every day is noise that gets ignored, including when a real drift lands. Resolve default paths via `expanduser`, never a hardcoded home from another OS (a Windows-style default on a Linux host makes every comparison wrong before it starts).
   - Broken frontmatter: typically unquoted `: ` in a description (YAML "mapping values are not allowed here") — report file + fix, don't edit (outside allowed writes).
   - **Bulk-import frontmatter damage:** a normaliser that joins fields emits one line like `description: ..." when_to_use: "..." last_reviewed: ...`; every file in that pack then fails `yaml.safe_load` with the same `mapping values are not allowed here` and loads with no name/description, so the router can never match it. Detect with a full scan (`for f in skills.rglob("SKILL.md"): yaml.safe_load(...)`), repair by rebuilding `name` + `description` and moving the extra keys into the body, and tar the tree first. Reusable repair: `scripts/repair_skill_frontmatter.py --root <skills dir>` for a dry run, `--apply` to write (archives every touched file, re-parses each result). A repair that makes N skills visible also grows the catalog — measure the new char count, it is a per-turn cost, not free.
   - **Duplicate names:** collision identity is NOT just frontmatter `name:`. Hermes resolves a skill by THREE aliases — declared name, **directory basename**, and path relative to the root — so a skill whose name equals another skill's *directory* name resolves `ambiguous` and `skill_view` refuses it. A declared-name-only scan reports zero duplicates while a whole capability is unreachable. Rename the DIRECTORY to its own frontmatter identity (never the skill) and both become addressable. Verify with `skills_health.py`, which now reuses Hermes' resolver and flags any entry with no `load_name` (excluding intentional cross-tier `shadowed` copies).
   - **Description budget is 60 chars.** The prompt index clips each description to `SKILL_PROMPT_DESC_LIMIT` (60, `agent/skill_utils.py`) at a word boundary. Scan for descriptions whose subject falls outside that window and rewrite only those with the trigger words first; descriptions that still read fine when clipped are not defects and mass-rewriting them is churn.
3. **Routing coverage** — read `skills/decide/SKILL.md`; verify the domain table covers: supabase, vercel/nextjs deploys, browser automation, elevenlabs-tts, ocr, comfyui/gpt-image-2, mlops (hf/llama-cpp/wandb), openhue, wix, music/audio, impeccable, stop-slop, od-* category, and all enabled MCP servers. **Empty category dirs that /decide routes to = dead routes** — patch the row to a real skill (2026-08-10 fixed: email→`email--himalaya`/`gmail`, research→`research--arxiv`/`research--blogwatcher`/`research--grounded-citations`, smart-home→`smart-home--openhue`). Keep the existing `| Trigger | Route To |` style.
4. **OpenDesign sync** — `python scripts/export-design-skills-to-opendesign.py` then `python scripts/import-opendesign-skills-to-hermes.py` (both idempotent). Steady-state output: export "plugins generated ~201, DB rows inserted 0"; import "imported 66, skipped (collision) 77" — 0 new is normal, not a failure.
5. **Cron health** — `hermes cron list` truncates the view at ~7 jobs: take `head -50` AND `tail -60` of the same command, or read `cron/jobs.json` directly. Flag `last_status: error`; read `cron/output/<job_id>/` for detail. Trivial-safe fix only: missing script path → copy the script into `scripts/` (see `hermes-cron-jobs` skill; `cron edit --script` rejects absolute paths). Note "Gateway is not running" warning — scheduler won't fire until started. Also run `hermes cron doctor` (lateness/catch-up warnings) and `hermes cron incidents` (durable incidents with resolved state). A provider outage poisons more than the job that surfaces it — sweep pins across cron jobs AND profile configs (`model`/`auxiliary`/`fallback_providers` blocks); see `hermes-cron-jobs` → "Provider balance failures". Paused/disabled jobs are audit items too: resume a paused watchdog only after verifying its blocking condition is fixed; a disabled backup job = lost coverage — surface it, don't assume it was intentional. Classify disabled-job errors separately from active regressions: record the failure and why the job is disabled before deciding whether any fix is warranted; never “repair” a deliberately paused job by re-enabling it.
   - **Backup cron error signature:** `storageQuotaExceeded` (403) = Drive quota (15 GiB), NOT a script bug. 2026-08-14 root cause: `state-snapshots/` (~1.1 GB/day rolling hermes-backup outputs) was inside BACKUP_ITEMS → every zip 2–3 GB → quota blown. Fixed: excluded state-snapshots (zip 2.06 GB → 657 MB), KEEP 5→3, cleaned `tmp/` staging junk that failed runs leave behind (~25 GB: `tmp/backup-account` + stale zips — script only cleans on success). Full detail in `workflow/hermes-backup-workflow` skill. If the error recurs, check `rclone about YOUR_RCLONE_REMOTE:` first.

6. **Plugin layer** — `hermes plugins list --json` for inventory (`--plain` for counts; the Rich table wraps and is unreadable), and `hermes tools list` for which plugin toolsets are enabled. A toolset can read `enabled` while the plugin behind it never loaded, so treat those two as different facts.
   - **Plugin skills can ship without a description.** `ctx.register_skill(name, path)` takes an optional description; a plugin that omits it lands in `<available_skills>` as a bare `plugin:skill` name with no trigger, so routing never fires even though the SKILL.md has one. Detect by rendering the catalog (`build_skills_system_prompt()`) and looking for plugin rows with no description; the root-cause fix is hydrating from the SKILL.md in `hermes_cli/plugins_content.py` (local patch #5, check: `~/.hermes/scripts/check_plugin_skill_descriptions.py`).
   - **A load failure is visible only in the log**: `grep 'Failed to load plugin' ~/.hermes/logs/agent.log`. Its tools, skills and hooks never register, while `hermes tools list` still shows the toolset enabled — the two are different facts. Diagnose before disabling: most such errors name a requirement (a profile secret scope, an owned state home) that one `plugins.entries.<name>.settings.<key>` line satisfies. Pin it, reload, then prove it with a real tool call from a NEW session. Disable only when the plugin offers no config path at all. Procedure and verification: `references/plugin-audit.md`.
   - Classify before calling anything unused: **active** (the configured provider selector points at it), **ready** (works with no credential, just never invoked), **blocked** (needs a key this profile lacks), **registry alternatives** (the other image/video/web/platform/dashboard backends — only the configured one runs; disabling them breaks the picker). For the memory family the selector is `memory.provider` and the evidence command is `hermes memory status` — it prints `Provider: (none — built-in only)` plus every installed provider, which is how a pile of enabled-but-inert memory plugins is told apart from a working one. Full decision table and evidence commands: `references/plugin-audit.md`.
   - **Overlap is a separate question from "does it work".** Invert `hooks:`/`provides_hooks:` across enabled plugins into hook → owners: `pre_llm_call` and `pre_tool_call` are the ones that run on every model / tool call, and when one callback is slow Hermes logs `Hook '<h>' callback <h> skipped after previous timeout or while still running` and then skips the hook's remaining callbacks — a gate another plugin provides silently does not run. Check tool-name collisions too (usually none, which is worth stating) before warning about "conflicts". Detail and the cost-reduction rule: `references/plugin-audit.md` → "Hook overlap".

7. **Utilization evidence** — inventory is not use. Measure from `state.db` read-only: `tool_name` counts over the last 30 days, distinct tools, `skill_view` targets parsed out of each skill_view row's `content` (it reads `[skill_view] name=<x> (N chars)`; `tool_calls` is NULL on those rows, so a `tool_calls` JSON parse yields nothing and reads as "no skills used"), sessions by source/model, and `parent_session_id` count for delegation. Two caveats decide whether the numbers mean anything: deferred tools (MCP and most plugin tools) record as `tool_call`, so count those by payload string (`content like '%"name": "<tool>%'`), never by `tool_name`; and a long-lived gateway caches plugin state, so a "missing" tool must be disproved with a real call, not a registry read. Expect the distribution to be top-heavy — a single integration can be most of all MCP traffic while a dozen others sit at single digits; that is a ranking for attention, not a delete list.

8. **Fixed cost and storage** — measure the four always-on prompt blocks (memory, skill catalog, SOUL, USER) and the `state.db` breakdown before proposing any optimisation; the levers, the memory-consolidation procedure and the offline VACUUM recipe are in `references/cost-and-storage.md`. Three measured facts that redirect most instincts: the skill index **clips every row at render time**, so shortening long descriptions saves literally zero chars (capping at 120/160/200 was measured at 0 gain) — the cost is row COUNT, and only removing or demoting whole skills moves it; the deferred tool listing is token-capped, so MCP server count is not a linear prompt cost; and pruning skills to save catalog tokens trades real capability for a rounding error unless usage data says the category is dead. Measure the catalog with `build_skills_system_prompt(...)` rather than summing `SKILL.md` bytes.

9. **Provider spend attribution** — when a bill or quota looks wrong, attribute it before theorising. `session_model_usage` grouped by `billing_provider, model` gives the agent's own share; whatever the agent's ledger cannot account for belongs to **another app on the same key**, and the usual cause is a *default* model in a coding-agent CLI's settings file, not an explicit choice. Procedure, unit traps and the guard pattern: `references/provider-spend-attribution.md`. When the decision is to remove the provider rather than demote its default, the route-table procedure is `llm-provider-wiring` → "Removing a provider from a route table".

## Integrated upstream references and improvement methods

The four-repository integration is recorded in `four-repo-integration-manifest.json`. Source checkouts live outside the active skill roots at `upstream-sources/four-repo-integration/`. Inspect their pinned commits and licenses before an update; never overwrite an adapted skill automatically. Compare upstream changes in a scratch clone, preserve local requirements, validate references and scripts, then use `skill_manage` for the accepted patch. Rebuild the existing discovery indexes after accepted changes.

For skill-improvement observations, reuse the existing background-review, curator, and audit structures. Do not create a second observer, schedule, or log. Before a single-target patch, evaluate likely family siblings and record whether each needs propagation, is already covered, is distinct, or was not inspected. Treat empty scans as an instrument claim until independently checked. A second unchanged rule failure calls for structural enforcement rather than another wording change.

These methods are adapted from Eoghan Henn's [Task Observer](https://github.com/rebelytics/one-skill-to-rule-them-all), commit `da860265ae968bdc6bb13b96c2c75fcb61176b72` (CC-BY-4.0). Only the portable review methods are adopted; its Claude hooks, observation store, and installer are not.

## Pitfalls

- **Reading config to find a provider setting can print the credential into the transcript.** A plain `grep` over `config.yaml` returns whole lines, so `api_key:` comes back verbatim and the redactor only masks values it recognises. Query structure without values (load the YAML and replace any key/token/secret field with `***` before printing, or use `hermes config get <dotted.key>`). If a key does get printed, say so plainly and tell the user to rotate it — a silent leak in a saved transcript is worse than the interruption.
- **A new watchdog check is only as good as the noise floor it lands in.** Before adding one, run the existing suite and de-noise any check that fires on a benign steady state (an idle launcher, a by-design profile gap): an alert that repeats every cycle trains the reader to ignore the whole channel, including the new check. The cheapest de-noising is a magnitude threshold — a browser-orphan check alerted on a 0%-CPU launcher until it required average CPU over the tree's lifetime.
- **A tool probe that opens a browser can outlive the probe.** Site-study, screenshot and record tools that keep a CDP session open hold a headless Chromium after the CLI exits; orphaned to systemd it keeps rendering with software GL (measured 877% of one core for 16 minutes). Close the session with the tool's own close command, or kill the process tree, and confirm with `pgrep -af 'headless=new'`.
- **Web search can be silently degraded while still "working".** `web.backend: nous` maps to Perplexity for search, so with no Perplexity key the resolver reports `not ready` and every call quietly falls through to a keyless free tier — searches succeed, doctor warns, nothing fails. Check the *resolved* provider, not just that a search returned results: load `agent.web_search_registry` and assert `_provider_is_ready(get_active_search_provider())`. If you pin `web.search_backend`/`web.extract_backend` to a provider, that provider may still need its own venv (`hermes pm install`) or every call hits `InstallError: lazy installs are disabled` and silently falls back again. Confirm with `hermes doctor | grep -E "web search|web extract"` showing `✓`.
- **A provider's own status command proves the FILES, not the running process.** The gateway snapshots its environment at start, so a key written to the env file afterwards is invisible to it: `hermes <provider> status` prints `ok: yes` and `api_key_configured: yes` (it reads config + the env file) while the first real call fails `API key not found` and quietly falls back to a keyless tier — one wasted request per call, no error surfaced. Before trusting any key-based provider in a live session, check what the process actually has: `tr '\0' '\n' < /proc/<gateway-pid>/environ | grep -c '^<KEY>='`. Zero means restart is required and nothing else will fix it; say so instead of re-running setup. The same rule explains a freshly registered MCP server whose tools ``tool_search`` cannot find — MCP discovery also happens at start.
- **Destructive-command approval prompts do not kill the run — they HANG it.** A confirmation-gated command (`hermes checkpoints prune`, force-push, `find -delete`) waits on stdin that no one will answer in an unattended context. In an interactive/audit session, prefix with `yes |` or check `--help` for a non-interactive flag rather than dispatching the bare command.
- **A runtime-immutable file blocks bulk deletes without failing loudly.** `rm -rf` on a tree containing a `d?????????`-mode entry (typical of an extracted archive) returns `Permission denied` for that path while reporting success for its siblings, and the parent dir survives. Check `ls -ldn`/`stat -c '%U %a'` on what remains before concluding cleanup worked; report such leftovers with their size instead of escalating to `sudo` over a few KB.
- **`hermes mcp list` shows `✗ disabled` for servers configured with `enabled: false`.** Reading the roster as a flat list of names and then filtering on a `disabled` key you invented produces nonsense coverage numbers. Filter on `enabled` from `config.yaml mcp_servers` and cross-check the actual `✓ enabled` column.
- **`hermes skills list` truncates the name column at ~14 chars with `…`.** A full-name grep then reports a present skill as missing, and the "fix" is deleting something that was fine. Verify discovery with a name[:13] prefix plus an on-disk `SKILL.md` count, or read the directory directly.
- **Removing a shadowed duplicate skill looks like a regression only if you grep the full name.** Hash-compare both copies first (`sha256sum`); an identical pair can be deleted from the lower-precedence location safely, and the surviving copy answers under the same name. A pair that DIFFERS is a deliberate local edit — keep it and say so.
- When `hermes doctor` says a package is missing but another doctor section says it is installed, probe the interpreter used by the Hermes entrypoint and the plugin loader before installing anything; Hermes has separate runtime, generation, and system Python tiers, so a package can be present in the wrong tier.
- `session_search` may not exist in cron environments — skip it, the job is self-contained.
- `find skills -name SKILL.md` in git-bash undercounts (path-length limits); trust the python glob (406 vs 288 observed).
- Skills named identically in `external_dirs` (e.g. `~/.agents/skills`) make bare `skill_view` ambiguous — use the local `skills/...` path.
- `search_files`/rg can throw "IO error: cannot find the file" on files that exist (hit on SOUL.md and scripts in this dir) — fall back to `read_file` or `grep` in terminal, both work.
- 10 minutes max for the MCP test loop; run it in background and poll.
- **No-agent cron scripts run on the generation venv, which is rebuilt on updates and does not ship PyYAML.** A checker that imports `yaml` dies at import; wrapped in a try/except it reports "health check failed to run" every cycle while checking nothing. Self-heal the dep (probe `shutil.which("uv")` + `~/.hermes/bin/uv`, then `uv pip install --python sys.executable pyyaml`) and verify the script under that interpreter, not just system python — a clean system-python run proves nothing about the cron path.
- Editing config/profile YAML: **`~/.hermes/config.yaml` is write-protected to the agent** — `patch`/`write_file` refuse it ("Refusing to write to Hermes config file: … security-sensitive"). Use `hermes config set <dotted.key> '<json value>'` / `hermes config unset <key>`, then re-read and `yaml.safe_load` to confirm (it rewrites comments, so diff the block you touched, not the file). Other YAML (profile configs, settings files) is not protected: there prefer targeted line edits over a load→dump round-trip. Regex-removing a nested block can leave its parent key as a bare `installs:` with a null value — re-print the parent after any structural delete, and restore from the backup you took if it collapsed.
