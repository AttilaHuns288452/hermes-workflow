# Design-option lookbooks — client chooses a UI direction

Purpose: ONE self-contained HTML page presenting the current design plus 2-4 genuinely different UI directions for the same app content, so the client picks one. The final build folds the chosen direction together with the review feedback ("middle ground").

## Procedure

1. **Mine the real app first** — grep the codebase for the dominant palette (most frequent color hexes), fonts, and navigation labels. The "original/current" variant must reproduce the live design faithfully (real hex values, real tab/label text) — never a recolor of it.
2. **Fix ONE content set** and render it in every variant (2 screens per variant: the primary screen + one data/list screen) so the comparison isolates design language. 3-5 variants total. When the product has multiple ROLES with distinct homescreens, the content set is one screen per role and the board becomes a grid (row per variant × column per role screen) — the isolation rule is unchanged.
3. **Each variant is a different design LANGUAGE, not a different hue** — vary at least 4 of {palette, type scale/face, density, navigation placement, corner-radius language, hierarchy (card vs row vs table), surface treatment (flat vs shadow vs glass vs dark)}. Count the varied dimensions before rendering; fewer than 4 is a recolor. **Palette-lock mode:** when the user requires one shared color scheme across all options — or stakeholders called the current UI "defaultish" (that is a LAYOUT critique of a generic app shell: card stack + icon grid + tab bar; recoloring never fixes it) — drop `palette` from the list and pull the remaining dimensions harder (5 of the other 7). Variety comes only from layout, structure, typography, scale, density, and surface. **Font consistency is its own lock:** when the user asks for consistent fonts (or flags mixed typefaces), every variant shares ONE stack declared once at the root (`body`) — strip all per-variant `font-family` overrides, serif included — and typography varies through scale/weight/case only. The new metrics un-fit every frame, so re-run the height refit across the whole board afterward (main skill's measure-pass pitfall). Semantic status colors (confirmed/completed/cancelled pills, refund amounts) and emoji glyph colors are functional, not scheme — keep them identical across every variant. Optionally include one deliberately-bolder option outside the team's stated guidelines, labeled as such.
4. **Per-variant spec strip**: name + one-line stance + palette swatches + strengths + trade-offs (what it gives up — e.g. large type costs density). The client chooses knowing the costs. **Text-free mode:** when the user asks for just the screens ("in a row, no other text"), drop the spec strips, captions, headers, and merge-note footer entirely — the row of frames IS the deliverable. Add labels back only if the user asks for them.
5. **Footer = how the decision gets made**: chosen option merged with the review feedback, plus explicit combination offers ("warm palette + minimal layout") — clients often pick pieces, not whole options.
6. **Author section-by-section**: write_file the document shell + first variant, then patch-insert each variant before a closing marker. A single timeout-sized write loses the whole file.
7. **Theme via CSS custom properties** scoped to each variant's section/frame container; keep ONE shared phone-chrome style so only the design language varies between frames.
8. **Verify + deliver per the main skill**: structural check AND vision pass over rendered frames (fix → re-render → re-vision), full-page PNG + one PNG per variant, artifact + PNGs to the project root and `~/Downloads` with a README pointer.

## Pitfalls

- Fixed-size frames clip rows (chip bars, icon-label rows) — build rule in the main skill's vision-flags pitfall; adjudicate inner-container clip claims per `browser-qa-playwright.md` (page-level overflow measurement does not apply). When content overflows a fixed-height mockup frame mid-element (a half-cut card reads as broken, not scrollable), fix by sizing frames to content, not by deleting content: measure each frame's scrollHeight vs clientHeight, then give each variant one height custom property (`height: var(--phoneH)` on the frame, `calc(var(--phoneH) - chrome)` on the screen) so a variant's frames stay uniform and nothing is cut. Deleting the overflowing block desyncs the shared content set the comparison depends on. (Deletion is legitimate when a content ban requires it — see the main skill's content-bans section — then refit the frame height instead of leaving a gap.)
- Inline-hex lookbooks have no token layer to remap: to recolor an already-built variant, split the file on the variant section anchors and apply per-section hex maps via script. Check each hex's usage contexts first — the same hex can be text ink in one variant and accent background in another — and replace contextually (e.g. only `background:` sites) rather than globally; keep neutral grays and semantic status colors out of the map.
- After any palette remap, the spec-strip chips are stale until edited — color-name words and hex values must match the new swatches (a "Warm canvas #F8FAFC" label after a warm→cool remap gets flagged). Add an explicit label-vs-swatch check to the vision prompt.
