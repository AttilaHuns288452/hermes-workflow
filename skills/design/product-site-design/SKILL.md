# Product Site Design (static, Figma-bound)

The deliverable is always a static site Attila will reproduce/import into Figma (prototypes = visual contracts). Optimize for hierarchy, spacing, typography, realistic product UI, and clean import — never for motion or effects.

## Standing direction (applies to every build)
1. **Real product company, never AI concept page.** Do not promote a metaphor (instrument station, nautical, terminal) to the whole visual personality. Borrow 2-3 characteristics, simplify. One signature concept per site max.
2. **~4 palette roles with dominance**, not one narrative color per section: warm off-white foundation (majority), primary dark (hero/footer/authority), ONE loud accent (CTA/key data only), gray for borders/muted text. A section's topic never earns it a new color. Severity/risk states = typography + weight + contrast, never extra hues.
3. **Zero fake telemetry.** No timestamps, unit IDs, AUTO-ON/LIVE lamps, window dots, status pills, floating label cards in mocks or chrome. At most ONE real measurement in the hero visual (e.g. '38/100'). State lists = plain quiet text.
4. **Mono = measurements + row index numbers only.** Labels/captions/footers/eyebrows = normal text.
5. **No em dashes in visible copy** — rewrite as two sentences or commas (meta/OG tags exempt). Benefit-first, natural product-team voice, no invented capabilities.
6. **Static/Figma-safe:** no animations, transitions, hover-dependent info, video. Radii: 8px controls, 12px cards, one 20px showcase. Flat elevation (shadow only on the one hero showcase panel).
6b. **Solid surfaces only — zero CSS gradients** on any brand surface (hero, CTA, footer, cards, charts). Depth comes from flat contrast steps, borders, and spacing; a gradient hero is the single most-cited 'AI-generated' tell in audits. Fixed chrome hidden when empty uses `display:none`, not transform offsets (full-page captures paint the leftover sliver).
7. **Editorial structure over card grids:** Hero -> Problem (numbered hairline list) -> Solution (alternating product rows) -> How it works (3 steps) -> Features (grouped 2-col list) -> Where it lives -> CTA. Product-as-hero: device render + one clean app screen.
8. **Honesty stays:** prototype/disclaimer lines and honest-drawbacks comparisons are a feature (trust), not clutter — keep them even when polishing.
9. **One data story across every product surface.** All device/dashboard/app mocks on a site share room names, status vocabulary, and the same numbers. An auditor will flag a surface saying "Watch" while its siblings say "Elevated" — unify the vocabulary before shipping.
10. **Removal test for polish passes:** "If I removed this element, would the visitor lose information, or would the design simply become cleaner?" Cleaner = remove. Never add content to fill whitespace; stop once the design is coherent.
11. **"Restrained" never means flat.** When the user calls a design boring/defaultish, the diagnosis is structural (every surface the same card weight, one type size, no focal point) — fix it with hierarchy, not decoration: exactly one focal anchor card owning the biggest type, one warm accent at <5% surface coverage (gold pairs with teal systems), and rhythm from type-scale steps, card-weight variety, tinted icon tiles, and eyebrow dots. Variety comes from LAYOUT first; effects (a subtle gradient moment, motion) only where the target's own brief permits them — rules 6/6b still bind Figma-bound static work. Deliver polish asks as a multimodal loop (vision critique → verify findings against pixels/computed styles → fix structural findings → one re-score), never a single decorate-and-ship pass.
12. **Desktop sizing bar: "too small" is a defect.** Attila judges at 1920x1080 and escalates undersized type and navbar chrome until it reads GENEROUS — a vision pass calling the chrome "comfortably typical or slightly generous" is the green zone, mere legibility is not. Proven fix: a ~20% bump of the whole desktop type scale plus a navbar chrome bump first (brand, links, search, buttons), side margins follow the width contract in 'Width & margin system' below, mobile keeps its tight scale. Measure rendered px via Playwright before and after; token names carry no size truth, and trust the vision verdict (GOOD SIZE / STILL SMALL) over its absolute px estimates — they run low vs rendered px.

## Scope docs are subtraction contracts
When Attila supplies a scope/requirements doc for a build ("check this is the scope"), audit the site AGAINST the doc and REMOVE everything beyond it — do not treat doc items the build lacks as gaps to fill and never start adding them. The doc defines the feature set exactly; out-of-scope extras (bonus pages, moderation powers, fabricated metric panels) are defects to delete. Sweep each removal fully: nav/sidebar links, JS router maps, store/API functions, test assertions, copy that references the removed feature, orphaned icon entries, column counts in shared table markup. Then verify: node test suite, headless E2E over every admin/public page with zero console errors, and the live URL (deleted pages must 404; grep the live JS for removed symbols — GitHub Pages CDN lags 2-3 min, cache-bust and re-check).

The doc is the ceiling AND the floor, but it is not scripture: when Attila challenges a doc item ("why is X here / we don't handle that"), that is a removal verdict, not a discussion prompt — answer the why in one line, then cut the feature in the same pass as any trim. A mid-task correction supersedes the doc; re-derive the feature set from the user's product model (who owns which responsibility), not from the original text. Removing a feature must not take its public-side read-only view with it — cut the management surface, keep the user-facing visibility.

## Admin-console scope (GadgetWise, fixed)
The admin area owns exactly: gadget CRUD (add/edit/delete, specs, mock product-API prefill), category CRUD, review moderation (approve/edit/reject), and view-only stats (users, gadgets, reports). It does NOT manage: reported issues (public-side info only — detail-page tab + report form), user accounts (no suspend/activate), data-quality audits, or export/import. When touching admin pages, preserve this boundary; new admin powers beyond it are defects.

## Procedure
1. Read the project's DESIGN.md / PRODUCT.md / claim register before writing copy (claims frozen; new capabilities are forbidden without a source).
2. Build/rebuild page(s) on shared tokens (site.css `:root`); page-scoped overrides via `<body class="page-x">` + `.page-x` selectors, appended CSS, never renames of classes other pages use.
3. Serve locally (`python3 -m http.server PORT`), then Playwright QA every page x viewport (1280x800, 390x844; add 320px and the user's judging width, e.g. 1920x1080): the overflow contract (document scan + leaf walk with rect adjudication, `scripts/overflow_scan.cjs`), 0 console errors, all internal links resolve, anchor targets exist + `scroll-margin-top` on sticky-header anchors, no `transition:/animation:` additions. Run the overflow contract in BOTH states of every persisted UI toggle (dev modes, filter sets): drive a hidden-by-default mode with `addInitScript` setting its localStorage key.
4. Copy sweeps (visible text only): em dash, UNIT/timestamps/AUTO-ON/LIVE, banned classes (`chip`, `lamp`, `kicker`, `hero-tag`, `statline`, `specline`). No kicker/eyebrow above any heading — ever.
5. One vision pass scoring ONLY 'brand maturity: looks like a real product company' with defects + positions; fix batch; one re-inspect. Stop polishing after that.
6. If a Figma board file exists, regenerate it (see reference) and verify it the same way. Commit + push + curl-verify the live URL before reporting done (prove it shipped by a changed bundle hash plus new symbols greppable in the built bundle; if a push with file changes stays 'blocked' while an empty commit deploys, follow with an empty 'Trigger deploy' commit).
7. Vision audit procedure (when the user asks to 'visually audit the UI'): shoot live full-page screenshots at 1440x900 AND 390x844 of every major page (Playwright chromium; see QA pitfalls for capture artifacts), run 1-2 vision passes with section-level questions, then DOM-adjudicate every finding with computed styles / getBoundingClientRect before editing. Fix, re-shoot, one confirm pass. Two delivery rules: the user reads English only — vision models sometimes answer in another language, so rewrite ALL vision output into English before it reaches a reply (never quote CJK fragments); and one giant full-page PNG can time the vision call out — prefer viewport-clipped or per-section shots when a page is long.

## Desktop scale-up (Tailwind v4)
Type utilities compile to `var(--text-*)`, so one unlayered `@media (min-width: 1024px) { :root { --text-*: ... } }` block scales every component on desktop at once while mobile keeps its 320px-clean scale. Line-height companions are unitless ratios and follow automatically (grep the built CSS for `--text-*--line-height` to confirm px vs ratio before touching them). Bump heading `clamp()` bounds alongside the tokens, then widen every fixed-width rem cell or track the old type was tuned to (price columns, score columns, sidebars) and re-run the overflow contract at ALL widths in both toggle states.

When type is hardcoded px instead of tokens (hand-written admin consoles, legacy CSS): put one `zoom` on the root that wraps everything (pages, modals, toasts), desktop-only (`@media (min-width: 1024px)`) — zoom scales type and padding together so layout cannot break, but it also inflates gutters (rendered gutter = CSS padding x zoom), so shrink horizontal padding to hold the width contract in 'Width & margin system' below. Never zoom at mobile widths: effective CSS width becomes viewport/zoom and 320 overflows. Any small hardcoded classes that zoom alone leaves too timid get bumped in ONE mapping pass per file (see `patch-hygiene`), never chained replaces.

## Proportional type system (type-size vs container balance)

"Margins look huge" → widen them → "now the fonts look small" → enlarge type → "now it's bloated" → shrink margins: that loop is a missing proportional link, not taste. Fixed-px type never tracks the container, so every container edit reopens type proportion and every type edit reopens density. Never answer one side of the loop with the other side's knob (do not widen containers to make type feel bigger, and do not enlarge type to fill a container); fix the system once:

1. **One multiplier knob for type.** Wrap every type token as `calc(base * var(--tscale,1))` and drive `--tscale` in the same viewport media steps as the gutters. Heading:body:price ratios and the label floor survive by construction because nothing is re-tuned individually. Never rebalance by editing individual sizes. Padding/margins never ride the type knob (scaling both recreates the bloat complaint); spacing gets its own knob, bumped only when a render shows cramped cards.
2. **Calibrate the knob from the design frame.** Measure the Figma PDF (pymupdf; see `reference-driven-implementation` → `references/figma-pdf-extraction.md`): artboard width, body/heading font px, gutter ratio. The frame's internal type ratios are exactly what a single multiplier preserves; use the frame-to-judging-width relationship to bracket 3-4 candidate values.
3. **Sweep candidates side-by-side at the judging width.** Element-clip the sections complaints come from (hero, dense list, steps, data chart) and montage at FIXED panel width (PIL grid). Height-normalizing panels balloons wide-short sections past legibility and destroys the comparison. Vision reliably picks the relative winner across a montage but misjudges absolute px; the frame-ratio bracket should corroborate the pick.
4. **Stopping condition = whole-page gestalt.** Full-page render at the judging width AND one lower desktop width, asked for "visually balanced as a whole" (not per-size nits), then the overflow contract at every width before shipping.

GadgetWise contract: base scale 14/16/18/20/24/30/38/44 × `--tscale: 1.25` at 1700px+, heading:body 2.1:1, label floor 14px.

## Width & margin system (container audit)
"Content feels narrow" or "margins are huge" is a container-system defect, never a padding tweak. For any width/spacing complaint: analyze the layout system before editing, fix the root constraint instead of per-page overrides, and iterate measure -> fix -> re-measure until geometry AND the gestalt pass; one change is never the stopping point. Type-size perception complaints ("fonts look small now") are NOT margin work: see 'Proportional type system' above; the container never compensates for typography.

1. **Inventory every container cap before touching values.** Grep `max-w-` across components AND container classes in global CSS (`.section`, `.container`, page shells), then tabulate caps per layer (chrome header/footer, public pages, admin). Competing caps across layers (e.g. 1200 on some pages, 1500 on admin, 1904 in chrome) IS the root cause: some pages read cramped while others hug the screen edges, and both extremes trigger complaints.
2. **Unify to ONE shell** (`max-w-[N]` + one gutter token set) used identically by chrome inner containers and every page shell. Derive N from two constraints together: reproduce the design frame's gutters at the frame's width (a 1440 Figma frame with 48px gutters -> `px-6 lg:px-12`), and hit the user's validated margin target at the judging width. The target is a hypothesis until the user confirms it perceptually: state the measured pixel gap in every reply, and when the user says 'half the margin' or reports the margins still big / the change invisible, cut hard to the extreme of the ask in ONE move instead of tuning again (a small incremental trim they cannot perceive reads as no work done). Final GadgetWise contract: full-width shells, no `max-w-` cap, responsive gutters 64px at 1920 / 48px at 1440 / 24px mobile (derived from the frame gutter ratio 50/1280 ≈ 3.3% at the judging width; the 24px-everywhere variant was rejected as too tight at desktop). Hold the validated gutter set LOCKED: re-tuning gutters after every type complaint is the oscillation the 'Proportional type system' section exists to break. Below any cap, pages run full-width with frame gutters (Figma fidelity preserved); above it, margins stop at the target.
3. **Text measure caps are not shells.** `max-w-[54ch]` prose limits, `max-w-md` forms, and hero-mockup internals stay as-is; widening them stretches copy, not layout.
4. **Chrome and content must share the exact cap + padding tokens** or header/nav edges misalign with page content at every width. Assert the header-inner vs content-inner left-edge delta per route with the geometry probe, not by eye.
5. **'No visible difference' after a verified deploy is a delivery problem first, not a CSS miss.** An open tab keeps the old SPA bundle alive indefinitely, page HTML caches for minutes after a push, and a legacy site URL often stays live beside its replacement, so the user may be measuring the wrong page. Before editing values again: confirm which URL they are viewing, grep the live hashed bundle for the new shell classes to prove the change shipped, then send a cache-busted link (`?cb=<timestamp>`) with a hard-refresh note and the before/after pixel gaps. Rendered-gutter ground truth = a column scan of a mid-page screenshot band (first non-background pixel column each side), not DOM box math alone.

## QA pitfalls (mechanisms, not anecdotes)
- **Overflow checks miss squeezed layouts.** A base rule defined AFTER a `@media (max-width)` block wins the cascade at equal specificity and silently cancels the stack — the grid stays 2-column on mobile with zero overflow to flag. Assert computed `grid-template-columns` count per viewport (2 desktop / 1 stacked), not just scrollWidth.
- **Full-page screenshots misplace sticky headers** — they paint at the capture scroll offset, so vision models report "header collides with content mid-page" that does not exist. Adjudicate EVERY vision geometry claim with DOM rects (getBoundingClientRect + scrollY) before editing anything. Element/clip screenshots have the mirror problem: `element.screenshot()` auto-scrolls the target to the top, where a sticky header paints over its first rows and vision reports "top row missing / clipped" — re-shoot at an offset below the sticky height before believing a top-clip claim. The crop edge fabricates clip findings too: text ending near the boundary reads as cut off (and montage panel edges do the same) — confirm the inter-element gap with getBoundingClientRect before fixing a clip that exists only in the screenshot. Pick capture targets by unique aria-label, not `page.$(sel)` first-match, which grabs the wrong widget when class names repeat.
- **Fixed-position chrome also paints mid-page in full-page captures.** Compare trays, toasts, and cookie bars (`position:fixed`, near-black backgrounds) render at the capture offset and read as a "stray black band / off-palette stripe" through the whole audit. Enumerate `position:fixed/sticky` elements and their computed backgrounds before accepting any stray-band finding. Hide empty fixed chrome with `display:none` (show = `display:block` + entrance animation), never `transform: translateY(110%)` — a transform only shifts the element by its own height, so a full-page capture still paints the sliver that pokes out, and every screenshot pass re-flags it.
- **Icon-left inputs and same-hue CTAs fail invisibly to functional tests.** An input's padding-left must cover the icon gutter (offset + width + gap) or the icon overlaps the placeholder — only screenshots show it. A primary button fails when its fill is the SAME hue as its surface (indigo fill on indigo hero reads disabled); the fix is contrast, not mandatory white — a brand fill ≥3:1 against a dark hero surface passes (e.g. electric blue on blue-charcoal ≈ 5.2:1), so compute the pair instead of pattern-matching 'dark hero → white button'.
- **A mock's essential surface must live on its own class,** never only on a wrapper-descendant selector (`.tile-mock .phone-ui { background }`). Redesigns drop wrappers; the descendant rule dies with them and the component renders white-on-white invisible. After markup changes, check computed `backgroundColor`/`color` of dark-surface mocks, not just that the class exists.
- **CSS purge regexes match substrings.** A removal pattern for `.p-num` also eats `.p-num .p-scale` and freshly re-added rules; line-anchored patterns miss descendant selectors (`.parent .child`) and compound selector groups. After any CSS surgery, verify the result with computed styles — source greps cannot see what the cascade actually applies. Removing a wrapper `<div>` also requires removing its matching close tag — assert open/close balance per section.
- **Lazy images false-report broken.** `naturalWidth===0` on below-fold `loading="lazy"` images is the no-scroll artifact, not a bug — scroll the page first, then assert. When a page has few images, drop lazy entirely so full-page screenshots (the user's defense artifacts) never capture blanks.
- **Long unbroken strings (emails, URLs) blow out grid cells.** `overflow-wrap: break-word` does NOT reduce min-content; use `overflow-wrap: anywhere` on the string + `min-width: 0` on grid/flex children. Diagnose with a leaf-overflow query (`scrollWidth > clientWidth` walk) before touching CSS.
- **`shrink-0` fixed-width children set a row's min-content wider than the 320 viewport.** A price/date block plus non-wrapping row text cannot shrink, so the row overflows even though every element fits at desktop. Make the row `flex-wrap` and give the trailing block `ml-auto` so it wraps and right-aligns at tiny widths; clipping is not the fix. Same min-content family as the unbreakable-string rule, different mechanism.
- **A clean document scrollWidth does not mean nothing overflows.** Content spilling its own box lands in the parent's padding/margin and never trips `scrollWidth > innerWidth`; children's border rects alone miss it too. The responsive gate is BOTH scans at every target width: document scrollWidth vs innerWidth, and a leaf walk flagging `scrollWidth > clientWidth`, then ADJUDICATING each spill against its parent's border box (spill past the parent = defect; spill inside a roomy parent = cosmetic, warn only). The overflowing leaf is usually wrapped text in a narrow fixed/`auto` track cell, not the obvious nowrap element.
- **Route probes must land on the intended route and prove it rendered.** HashRouter/SPA apps serve the home route for any path missing the `#/`, so probing `/gadgets` silently measures home and returns identical, falsely clean numbers for every route; a malformed probe URL can load a near-blank page whose `scrollWidth === innerWidth` passes the overflow gate. Navigate router-correct URLs (`#/gadgets`, `#/compare?ids=...`) and assert a page-identifying marker before recording any measurement.
- **Auto grid tracks size to max-content and never shrink below it.** A wide child (tab strip, table) stretches an implicit or `auto` track past the viewport, and `overflow-x-auto` on the child clips only its own content — it does NOT stop the track from stretching the page. Give the stacked mobile view an explicit `grid-cols-1` (minmax(0,1fr)) and `min-w-0` on content columns before blaming the child.
- **Themed Tailwind scales lie about size.** A project's `@theme` can redefine `text-xl` to 30px+; the token name carries no size truth. When text overflows a cell or a layout "shrank" unexpectedly, read computed `fontSize` first and re-measure rendered px after every class swap instead of trusting the token name.
- **Undefined fields render blank in JSX with no error.** A derived row referencing a field the domain object lacks (e.g. `name` vs `brand`+`model`) ships empty cells that look like a CSS bug. Derive display strings at the data seam and assert every derived display field is a non-empty string in the node check suite, so the build fails instead of shipping blanks.
- **Vision findings need DOM adjudication** for load-state questions (gray box vs failed image) — screenshot passes do not trigger lazy loads. UI-state claims hallucinate too ("two filter tabs active", "button disabled"): assert className/aria state in the DOM before "fixing" a state that is already correct. Color and contrast claims are equally unreliable: vision routinely reports high-contrast pairs as 'low contrast' and mid-tone gradient fills as 'invisible' or 'muted'. Before editing anything color-related, compute the actual pair (getComputedStyle fg/bg + WCAG ratio) and sample the pixels; fix only the structural findings (clipping, truncation, hierarchy, alignment) and reject color claims the ground truth contradicts.
- **Meta/OG tag content is exempt** from visible-copy sweeps; strip comments before grepping so review-note text does not false-positive.
- **Class-usage assertions via `page.content()` regex also match the injected stylesheet** — a generated `.bg-gradient-to-br` rule makes `content().match(/bg-gradient/)` count even with zero elements using it. Count real elements instead (`page.evaluate(() => document.querySelectorAll('[class*="bg-gradient"]').length)`).
- **When a user directive supersedes a policy an existing QA check encodes, retarget the check, never delete the guard.** A zero-gradient policy superseded by 'don't look boring' becomes a DOM-counted 'subtle gradients only, ≤2' assertion — the regression value survives the policy change.
- **JSON fixtures embedded in the DOM decode silently wrong through JSX text nodes** — React escapes braces and `decodeURIComponent` of the mangled string returns %-garbage instead of throwing. Verify seeded demo data by counting JSON-decoded elements and re-reading the parsed payload, not by eyeballing the rendered page.
- **A type scale-up overflows the cells the old type was tuned to.** Fixed-rem grid tracks (price column, score column), fixed sidebar columns, and fixed-width `truncate` columns clip, wrap, or ellipsize text that previously fit the moment type grows; widen them in the same change-set as the bump (widen the column or drop `truncate`), then re-run the overflow scans at every target width including 320.
- **Token migrations leave stragglers outside the swept size list.** Converting hardcoded `text-[Npx]` by a known pair list silently misses sizes nobody listed (one `text-[26px]` heading keeps the old scale while 22/32 convert). Inventory EVERY px literal first, classify each (convert to the scale or keep as a deliberate sub-level), then grep the tree back to exactly the classified survivors.
- **Chrome bumps at the base breakpoint break 320 first.** A toolbar row (search field + buttons) without `flex-wrap` grows past 320px as soon as paddings and text rise; put the growth behind `sm:` prefixes and make toolbars wrap, so desktop gets the size and mobile keeps its tight, QA-clean chrome.
- **Shell padding utilities collide with component padding.** `px-5`/`px-6` also sit on cards, table cells, and button rows, so normalize shells by unique multi-class context strings, never a global utility replace. Shell class lists usually SPLIT cap and padding (`max-w-[...]` and `px-...` separated by unrelated classes) — one contiguous replace_all silently misses them; grep the old caps and old shell paddings back to zero after the pass.
- **Geometry probes keyed to shell class names go stale the moment the shell is renamed** in a tuning pass: the probe reports shell=0 / absurd margins while the app itself is fine. Update the probe's selector in the same change-set as any shell class rename, and never bend app classes to match a stale probe.
- **Widest-element probes misreport content width on full-bleed bands.** Hero bands and stats bars legitimately span the viewport, so "measure the widest element" invents fake margins. Measure only the elements carrying the shell classes, and report left/right margin + header-content edge delta + document overflow per route.
- **Vision gestalt comes after deterministic geometry, never before.** Gate layout fixes on measured shell width/margins/edge alignment/overflow across 320-1920; use vision only for the final "does it feel balanced" verdict. Nits about pre-existing frame characteristics (hero column balance, a search/sort toolbar gap) are design, not spacing defects — leave them.
- **Client-side data overlays persist between Playwright runs.** Prototype admin CRUD backed by a localStorage store survives in the default browser profile, so an E2E run can assert against a prior session's edited dataset instead of the shipped one (stale counts, phantom rows, masked regressions). Launch a fresh context with `addInitScript(() => localStorage.clear())` before any dataset-count or render assertion, and never trust a "clean" first-pass E2E that silently ran on modified data.

## Parallel build pattern (multi-page sites)
Dispatch 2 subagents with DISJOINT file ownership (agent A: index + shared css/docs; agent B: the other pages), each told 'YOU OWN exactly: ... DO NOT touch: ...'. Same working tree, no conflicts. Steer running children for mid-flight directives. On return: verify independently (own greps/screenshots) — child reports are self-reports.

When delegating vision audits, require geometry cross-checks: every flag must be verified against DOM computed styles/rects before it is reported (this rejects most vision hallucinations — invented buttons, phantom telemetry, artifact collisions). State the design intent in the brief so auditors judge execution, not direction; in final-polish mode explicitly instruct them not to recommend adding content or sections.
