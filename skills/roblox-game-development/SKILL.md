# Roblox game development (Luau / Rojo)

## Never take the user's screen

Before launching Studio or sending it input, run `studio-guard`. Exit 0 = safe; exit 1 = the person
is playing, a fullscreen window owns the screen, or DND is on. On exit 1, stop: do not launch, do
not click, do not type. Use `studio-guard --wait 900` for background work that can yield, and
`--dnd on` if the user wants to block all Studio automation manually.

## When to Use

Any Roblox experience work: creating a game from a design brief, adding gameplay systems, refactoring Luau code, verifying a build, setting up Studio tooling on Linux, or wiring the Studio MCP. If the deliverable is a .rbxlx/.rbxl place or a Rojo source tree, this skill governs.

Build the game as a Rojo source project with a real verification chain. Studio time (and the Studio MCP) is the LAST step, never the first: everything testable outside Studio is tested outside Studio.

## Standing rules (owner requirements)

- **Never call a build "done" without running its gates in the same turn.** This owner checks claims; a delivered artifact is reported with the real command output (test counts, build size, clean tree), and anything unverified is named as unverified in the same breath. "It should work" is not a deliverable.
- **Playable vertical slice before world expansion.** The first version must already contain: tutorial area, one main hub, the core earn loop, the main debuff/progression mechanic, currency + upgrades, a social multiplier, 2 small activities, a collection journal, rare discoveries, hidden collectibles, and save/load. That is the fun-validation gate; only then expand the map and add systems.
- **The acceptance checklist is a real release gate.** Every row gets labeled Passed / Failed / Blocked / Not yet tested honestly. Never declare the game complete because scripts were generated; a statically verified build that has not been playtested is reported as unplaytested, and runtime blockers (e.g. Studio not installed) are surfaced as blockers.
- **`src/shared/Config.luau` is the numeric authority.** All tuning (economy rates, upgrade curves, zone tables, reward caps) lives in one typed Config module; docs reference it and never fork values into prose.
- Deliverables go in the repo root AND `~/Downloads/<Project>/` (place file, README, QA report), per the owner's standing convention.
- **"Polish" and "complete the game" mean PLAYER-FACING completeness, not more systems or more tests.** When this owner says the result is "still not enough", the answer is a visible change in the running game — sound that plays, models that read as models, a world with density and atmosphere — not another green suite, another refactor, or a restyled panel. A fixed bug is invisible to them until it renders. Rank remaining work by what a player SEES and HEARS in the first five minutes, and treat unimplemented audio or primitive-only art as a blocking gap rather than a polish note.

## Polish missions (contract-driven loops)

When the owner hands a polish contract ("zero P1s open", "loop until the game is finished",
"everything you are allowed to do"), run it as a ledgered loop instead of ad-hoc fixes: capture and score
every screen FIRST, rank the defects in a machine-readable file, fix one per pass at the owning layer, and
prove each one with a before/after pair from the same camera station plus the numeric gate. The artifacts
(`LOOP.md`, `DEFECTS.json`, `ART_DIRECTION.md`, `FINAL_REPORT.md`, `STATUS.md`), the pass order, the commit
discipline and the stop conditions are in `references/polish-loop.md`.

Two always-on rules for that work:

- **A shared defect is fixed once, in the shared layer.** Ten panels with 28px close buttons is one pass in
  the module that already walks every panel (grow to 44 around the centre, set the text floor, remap the
  legacy colour), not ten file edits that drift apart by the next session.
- **An accepted defect needs a written reason.** "Open" and "accepted" are different states; silence about a
  known defect reads as an oversight, while `accepted: <why>` reads as a decision.

## Procedure

0. **Mission/ROI briefs: audit first, then gap-fill — never re-derive.** When handed a long design directive against an existing project, do NOT start from the brief's document. Inventory what exists by grepping the source for each named system, tag a recoverable checkpoint (`git tag pre-mission-checkpoint`), and open the work by listing which brief items are ABSENT. Then build only those, in ROI order (does it change retention/spending > is it visible > is it polish), reusing the existing Config/service/UI shapes rather than inventing parallel ones. Report gaps-vs-brief explicitly so "the brief said pets" is answered with "five pets now, here are the numbers". A brief that asks for a feature you already have is an opportunity to prove it with a test, not to rebuild it.
1. **Probe the environment first.** `flatpak list | grep -i vinegar`; an empty `~/.var/app/org.vinegarhq.Vinegar/data/vinegar/` dir means Studio was never installed (the flatpak alone is not an install). The install itself is agent-doable (`flatpak run org.vinegarhq.Vinegar install`, never piped — see the reference for pitfalls); only the Roblox OAuth login click is a HUMAN step — never type credentials. Record any gap honestly in QA/known-issues docs.
2. **Scaffold a Rojo project** (`default.project.json`): `ReplicatedStorage/Shared`, `ServerScriptService/Server`, `StarterGui/Client`. Git init immediately. Use `StarterGui`, NOT `StarterPlayerScripts`, for the client tree — see the pitfalls.
3. **Shared contract layer first** (it is the inter-module API): `Config.luau` (typed tables), pure logic modules (economy math, debuff logic, save schema), and a small `Remotes.luau` wire factory. Pure modules: zero requires, zero Roblox API.
4. **Test harness under standalone luau**: `tests/run.luau` with `require("../src/shared/X")` (luau CLI require-by-path works). The one runnable check covers cost curves, multiplier tiers, debuff rules, and save merge/migration.
5. **Server services** (data/persistence, the earn loop, debuff runner, upgrades, journal, activities, tutorial) wired through ONE bootstrap dispatcher. Build the world at RUNTIME (a `MapBuilder` module constructing anchored parts) so the place file ships without hand-built geometry and the whole game stays code-reviewable.
6. **Client**: a shared `ClientState` module (snapshot cache + request helper) + one LocalScript per surface (HUD, menus, controllers).
7. **Verification chain — run ALL of it before claiming the build is sound:**
   - `luau tests/run.luau`
   - `rojo sourcemap default.project.json -o sourcemap.json`
   - `luau-lsp analyze --definitions=tools/globalTypes.d.luau --sourcemap=sourcemap.json src/` → must be ZERO errors (defs file from the luau-lsp repo, kept in `tools/`)
   - `rojo build -o <name>.rbxlx`, then audit the instance tree inside the XML (script names must land in the right services).
8. **Docs as honest status**: README (how to open/run + what is verified), QA_REPORT.md with the label table, KNOWN_ISSUES.md with deliberate scope cuts and ponytail-marked simplifications, plus the design docs the brief requires (GDD, architecture, economy) that point at Config as numeric authority.

## Pitfalls

- Luau has NO field-annotation assignment: `Config.X: T = {...}` is a parse error ("Expected identifier when parsing method name") and can mask as silent breakage downstream. Type via `local x: T = {...}` then plain `Config.X = x`.
- Rojo `init.server.luau` / `init.client.luau` merges the folder INTO that script and siblings become its children — every `require(script.Parent.X)` silently becomes wrong (it must be `require(script.X)`). If you wrote sibling requires as `script.Parent.X`, name the entry file `Bootstrap.server.luau` instead so the folder stays a Folder.
- RemoteFunction responses: return ONE `{ok = boolean, result = any}` table from `OnServerInvoke` and unwrap it in exactly one client helper. Multi-return truncation risk is not worth it, and multi-value returns trip the analyzer's `InvokeServer` typing.
- Heterogeneous tuple tables (`{ {Vector3, CFrame} }`) infer union element types and error at every index site. Use named typed records (`{ size: Vector3, cf: CFrame }`).
- Wire-contract evolution: when a subsystem change makes a Request/Action kind obsolete (e.g. the server now derives a signal the client used to ping for), resolve it explicitly — remove the kind from client callers, the dispatcher whitelist, and CONTRACT.md together, or keep it as a documented accepted no-op. A half-removed kind becomes either a rejected-request error stream on live clients or a contract doc that lies.
- Vanilla `luau-analyze` has no Roblox API defs — every `game`/`Instance`/`Enum` use reads as UnknownGlobal and real errors hide in the noise. Full fidelity = `luau-lsp analyze --definitions=globalTypes.d.luau --sourcemap=...` (sourcemap resolves `script.Parent.X` and instance-tree keys like `ReplicatedStorage.Shared`). Get BOTH files or you are not really checking. Regenerate the sourcemap whenever files are added — a stale one yields bogus `Unknown require: unsupported path` errors that read exactly like real bugs and send you debugging correct code.
- In a built `.rbxlx`, instance names are element VALUES (`<string name="Name">Foo</string>`), not XML attributes — grep accordingly when auditing the place file.
- Roblox-dependent code cannot run under the luau CLI *as written*: plain `luau` has no `game`/`Instance`/`Enum`, and its `_G` and `os` tables are READONLY, so you can neither install globals nor fake time. That is a staging problem, not a design ceiling — stage the real modules with rewritten requires plus a mock API (see `## Headless simulation harness`). Do NOT re-architect the game into require-free fragments just to make it testable, and do not accept "untested because it needs Roblox" while a build is still unplaytested.
- A reset must produce the FULL shape, not an empty table. `data.upgrades = {}` after a rebirth leaves every level `nil`; readers that index `upgrades[id]` directly (client UI rows, any `1 + lvl * x` without `or 0`) then read nothing. Zero every configured key from Config (`for id in Config.Upgrades do data.upgrades[id] = 0 end`) so the reset cannot leave holes.
- Simulator pacing is a defect surface, not a taste question: compute time-to-milestone from `Config` (cost ÷ income) and compare it to the design targets before calling an economy "balanced". A first upgrade at 10 minutes and a first prestige at 66 hours passes every lint and test while being unshippable. Assert the bands in the runnable check (e.g. first upgrade ≤ 3 min, first rebirth inside 20-120 min at the starter zone) so a later retune cannot silently regress them, and scale one-time rewards with any income change to keep their relative weight.
- Server security shape: one Request dispatcher with a kind whitelist, per-player rate limit, `pcall` around every handler, and a data-loaded gate. Never scatter `OnServerInvoke` handlers across services — one choke point is a smaller audit than N.
- Player data discipline: merge loaded data over defaults (explicit zeros must survive), never persist a half-loaded session over good data, and degrade DataStore failure to in-memory play so the game still runs in Studio without API access.
- Save-schema migrations must defensively default EVERY table a branch indexes, not just the fields that branch adds — an older save can arrive without tables that newer code assumes (`data.stats.x = data.stats.x or 0` crashes when `stats` itself is nil). Give each legacy version a fixture in the runnable check (v1 input, v2 input, ...) so every migration branch is exercised, not just the newest.
- World-interactive parts are located by exact name from services (`CollectibleSpawn_<id>`, `RareGrassSpawn_<id>`, `Firewood1..3`, `CampSeat1..4`...). Treat those names as a contract: rename in MapBuilder and every service locator together, or grep the name before renaming.
- A named spawn part is inert until the map builder attaches the `ProximityPrompt` the client hooks. Without it the feature never fires and NEVER ERRORS — an entire collection system can sit at 0/N forever with clean lint, clean tests and no warning. Before trusting a client `Triggered` hook, assert the builder creates a prompt on every part of that family; one `prompt(part, ...)` line per spawn is the whole fix.
- Client-reported numbers are claims, not facts. Any value the client sends that feeds a reward (distance travelled, peak speed, participant count, step completion) must be bounded by state the SERVER observed, or it is fabricable at the remote rate limit. Record an anchor when the action starts (position, timestamp) and clamp the claim against what happened since; a claim with no observed movement must collapse to zero reward. Put the bound rule in a pure shared module so it leaves a runnable check — an untested clamp is how the exploit gets silently reopened by the next edit.
- Fixed-pixel GUI geometry does not survive a phone. A panel wider than ~360px clips off the screen with no error, and mobile-usability is an acceptance row on most briefs. Add one `UIScale` per `ScreenGui` derived from viewport vs a design size (largest panel + margin), capped at 1 so desktop keeps native size; `UIScale` scales around the GUI origin, so anchored and edge-offset elements keep their positions and only shrink. Verify by measuring panel widths against a 360x640 viewport instead of assuming.
- Character-scoped connections must be re-established on `CharacterAdded` and the previous one dropped. Bound once to the humanoid at script start, the hook dies silently on the first respawn and the feature stops working for the rest of the session; bound per respawn without disconnecting, it leaks a connection and a dead closure every life. Both fail quietly. Keep one upvalue connection and swap it, or the behaviour is untestable by inspection.
- Screen-GUI buttons anchored to the same edge share one absolute coordinate stack — there is no layout manager across separate ScreenGuis. Before placing a new toggle/menu button, grep the existing client scripts for that edge's `UDim2.new(1, ...` / `toggle.Position` values and continue the stack below the lowest one; overlapping buttons (e.g. a pet button sitting on a slide button) are a playtest-visible defect, not cosmetic. Better: give ONE module ownership of the rail — a draw-order pass already walks every ScreenGui, so let it set width, colour, anchor and stacking for every direct-child TextButton instead of editing ten files that each hardcode their own accent colour. Order those toggles by a PRIORITY list, never alphabetically: alphabetical is deterministic but buries the premise button mid-stack and pushes a movement verb to last place. When a test asserts the rail does not overlap, sort the collected buttons by their calculated Y coordinate rather than re-deriving the intended order — otherwise the assertion fails every time the priority list changes.
- **Raising a Frame's `ZIndex` paints it over its own children.** Roblox sorts every GuiObject in a ScreenGui by absolute ZIndex and children default to `1`, so the moment a draw-order pass lifts panels to `ZIndex 10` to clear a button rail, each opaque panel is drawn AFTER its own labels and renders as a blank coloured card. Nothing errors, and a geometry audit passes, because the text exists at the right coordinates — it is simply underneath. Push the layer down the subtree (`child.ZIndex = z` on every descendant) and assert no label sits below its parent frame. This is the defect that makes an ENTIRE UI read as empty while every other gate is green, so check it before restyling any panel.
- Feature wiring in a one-dispatcher architecture fails SILENTLY: a new gameplay system touches shared module + server service + `start()` call + dispatcher handler entry + the state snapshot's fields + client UI, and any missing layer yields a dead button or empty panel instead of an error. Mirror an existing handler of the same shape and tick off every touchpoint before testing.
- `StarterPlayerScripts` does not clone its LocalScripts into the character under Studio-on-Wine — they silently never run, and nothing errors. Build the client tree under `StarterGui` instead. The same clone is also the reason a sibling `require` must go through `WaitForChild`: the script is live before its siblings are parented next to it, so a bare `script.Parent.X` require races and fails only on some joins.
- Status docs (QA report, completion audit) accumulate DUPLICATE tables and contradictory verdicts across successive audit/fix passes — the same defect table appears twice and two different "current verdict" lines survive. Before delivering, reconcile to ONE current verification matrix and ONE release verdict: delete superseded duplicate sections and stale per-pass tables instead of stacking them, and quarantine older evidence under a clearly-labeled "historical / not fresh" heading so it is never read as current. A QA doc that still carries two copies of the same table reads as unreconciled work and erodes trust in every number in it.

- **A `while true` background loop dies permanently on the first error, with no symptom.** Farming, achievements, pets, activities and the world clock all run in `task.spawn(function() while true do ... end end)`; one nil field or destroyed instance kills that coroutine and the system is dead for the rest of the server's life — no error, no retry, the feature just stops. Wrap every such loop in a `Guarded.spawn(name, body)` helper that pcalls the body, warns with the system name, and restarts after a pause. Prove it by crashing a loop on purpose in the harness and asserting it keeps running.
- **Parts parented to a character must be WELDED, never Anchored.** An `Anchored = true` part parented to a character stays at the CFrame where it was created, so the player walks out of a hat, aura or pet and it hangs in the air. Build the visual, set `Anchored = false` + `Massless = true`, then `WeldConstraint` it to the head/root.
- **`StarterGui.ResetPlayerGuiOnSpawn` defaults to true and duplicates your entire UI.** Every LocalScript under StarterGui re-clones into PlayerGui on respawn, and each one builds a ScreenGui with a fixed name — die once and the player has two of every panel stacked. Set `"ResetPlayerGuiOnSpawn": false` in the place's `$properties` for StarterGui, and assert panel names stay unique across a simulated respawn.
- **Overlapping ground/zone parts need a specificity rule, not a first match.** A sub-zone drawn on top of a big zone (a garden plot inside a park lawn) returns whichever happened to be tagged first, so standing on the 80 GP/min plot pays the 50 GP/min lawn. Resolve to the SMALLEST matching footprint, and assert the specific rate wins.
- **Start always-on systems from the always-running client script.** Audio, HUD wiring and prompt hooks were initialised inside a menu's LocalScript, so nothing existed until the player opened that menu — most players never heard a sound. Initialise cross-cutting client layers in the HUD script (the one that always runs); menus should only read state.
- **Client hooks that scan the world at load race the server-built map.** `workspace:FindFirstChild("Campsite")` runs before the server's Map replicates, so a fast-joining client wires nothing and camping/collectibles are silently dead for that session. `WaitForChild("Map", 30)` first, then hook `GetDescendants()` AND `DescendantAdded` so prompts created later are still wired — and dedupe with a hook flag so a re-scan cannot double-connect.
- **Two upgrades that multiply the same thing at the same rate are one upgrade.** `TouchSpeed` and `TouchStrength` both gave +5%/level to passive income while one cost more: the dearer one is strictly dominated and nobody would ever buy it. Every upgrade must move a DISTINCT axis (passive income vs activity payouts vs journal rewards vs debuff rate), and its `effectDesc` must describe what the code actually does — a description claiming "rare grass luck" for a payout multiplier is a lie the UI tells the player.
- **A stat or currency that accumulates forever and does nothing is an unimplemented feature.** Pet friendship rose on every feed with no consumer; EP was awarded on every prestige, shown in the HUD, and had no sink at all — a veteran's entire prestige currency was a trophy. Before shipping, grep every persisted counter AND every earned currency for a reader/spender; give each a threshold payout or a sink the player chooses between, or delete it. A level computed from XP and displayed but never gating anything is the same defect.
- **`PartType.Cylinder` runs along its X axis, not its height.** A cylinder sized `(0.25, 5, 5)` intending a flat disc (hat brim, pot lid, lamp shade, plate) renders as a vertical plate FACING the camera, because the flat faces point along ±X. Multiply by `CFrame.Angles(0, 0, math.rad(90))` to stand it up. Vision reviewers read the resulting plate as a halo, a glow or a bug rather than a misoriented part, so the symptom never names the cause — if a circular element "floats behind" something, check the roll before restyling it.
- **A rotated slab's authored sign is a guess until you compute both end heights.** `CFrame.Angles(math.rad(-20), 0, 0)` on a long part raises its +Z end (Rx maps local +z to +y), so a ramp meant to descend toward the park descends toward the summit instead: the hill reads as a green trapezoid from every angle and the downhill push vector drives the player INTO the surface. Before trusting a slope, compute the surface height at both ends (`cf * Vector3.new(0, thickness/2, ±length/2)`) and compare them to the two things it must meet (the summit platform, the runout); derive the angle from the height difference (`atan(dy/dz)`), and change every consumer of the slope direction (slide vector, activity gate) in the same edit. Same rule for any authored tilt where the visible defect is "it looks like a wedge".
- **A meter whose number means "absence of the bad thing" must render as health, not as the raw stat.** Deprivation/hunger/heat that defaults to `0` on a new save drives a literal progress bar to zero width, which reads as an unloaded or broken UI element on the very first frame while the underlying value is perfectly healthy. Invert it (`health = 100 - value`) so a new player sees a FULL bar that drains, keep the colour thresholds on the raw value, and comment why; no amount of restyling fixes a bar that is correctly empty for a good reason.
- **`Config` is pure data — no Roblox value types in it.** It is required by the pure-logic test with no Roblox API present, so a single `Color3.fromRGB(...)` in a config table breaks that whole gate with `attempt to index nil with 'fromRGB'`. Store colours as plain RGB number tables and convert in the service that consumes them (`Color3.fromRGB(v[1], v[2], v[3])`).
- **An alt-account ring is the cheapest social-multiplier exploit.** Account age is the only signal a server gets (no IP, no device id), so weight young accounts at a fraction (e.g. under 7 days = 0.5) when COUNTING participants toward a tier — never zero, or genuine new friends are punished too. Assert five day-one accounts score below five established ones while a real group still beats solo.
- **A debuff needs a visible body change, not just a number.** A deprivation mechanic that only prints a stage name is a stat nobody notices. Lerp body-part colours toward a stage tint and add a removable overlay part (eyebags) at the bad stages, remembering each part's original colour so recovery is lossless. Parent that overlay to the character and look it up on the CHARACTER afterwards — welding it to the head but searching under the head means recovery can never find it and the player keeps the eyebags forever.
- **A prop family needs one name PREFIX, not per-instance names.** Naming seats `DuckPondSeat`/`QuietPondSeat` while the server guard matches `^Pond` rejects every real instance, and no test notices until one is written for it. Generate `Prefix_<variant>` from the builder and match the same literal prefix in every consumer (server gate, client hook, test).
- **Repeated props read as placeholder until each instance VARIES.** Fifteen identical trees — same trunk, same three canopy spheres, same height — read as a stamped asset field no matter how well one tree is built, and the reviewer's word for it is "blockout". Derive per-instance scale, lean and tint from the instance's own coordinates (`local t = ((x*7 + z*13) % 100)/100`) so the park is varied yet byte-identical on every server boot. A time- or `math.random`-seeded layout is non-reproducible: it breaks any test that counts, measures or screenshots props.
- **A sound id is a CLAIM until you list the client's `content/sounds/` folder.** `rbxasset://sounds/button.wav`, `electronicpingshort.wav`, `snap.mp3` and `victory.wav` do not ship with the client, so every `Audio.play()` 404s SILENTLY: the audio module, the volume sliders, the persisted settings and the `Audio.play(kind)` call sites all look implemented while the game is completely mute and every gate stays green. Enumerate the real set before wiring anything — `ls ~/.var/app/org.vinegarhq.Vinegar/data/vinegar/versions/version-*/content/sounds/` returns ~11 files (footsteps, jump, jump_land, landing, swim, water impact, falling, oof, ouch, volume_slider) — and keep the kind→file mapping in `Config`. There is **no bundled music** in the client at all, so a background track requires an asset uploaded to the creator account; budget that as its own task, and note Studio's Import dialog accepts only FBX/OBJ/GLB/GLTF, i.e. it is the MESH path, not the audio path.

## Onboarding

A new player's first minute is a feature, not a tooltip. One toast at spawn ("Talk to the NPC, then touch grass") is not a tutorial: it disappears in four seconds and leaves nothing on screen.

- **Derive steps from state the game already tracks.** Talked, a completed farm tick, an upgrade bought, a reachable zone tick, a discovered entry — these already exist as counters and registries. Adding a parallel `tutorialStep` flag creates a second source of truth that drifts the moment a player skips ahead. Compute `currentStep(data)` as "the first unmet condition" so skipping cannot dead-end and nothing new needs saving (a single new counter, e.g. park ticks, is the whole budget).
- **Put the objective on the HUD, persistently, driven by the ordinary state push.** Publish `tutorialStep` on the snapshot rather than adding a remote, and render `N/M <what to do now>`; hide it when the chain completes. A step the player cannot see is a step they will not do.
- **Step order must match world geography, and the test must assert it.** An ordering that asks the player to find a collectible before they can reach the zone it lives in is impossible, not merely awkward — every species spawned in the park while the "find a species" step preceded the "walk to the park" step. Assert the reach-then-collect ordering as an invariant so a later reshuffle cannot reintroduce it.
- **The first objective must be VISIBLE from spawn, not merely reachable.** An interior spawn area lit by one weak lamp (brightness under 1, range shorter than the room) reads as a black void, and a tutorial NPC 50 studs away in it is unfindable even though the HUD names it. Light the spawn space so the far wall is legible and mark the first target with a beacon (a tall Neon part plus a PointLight), then assert it in the harness — lamp brightness/range floor and the beacon part's existence — so a later map edit cannot silently re-darken the first minute of the game. Reachability tests pass here while the player still stands in the dark. **Calibrate the intensity instead of guessing it — the right number is not derivable from code:** in a roofless 120x120 room a point light at brightness 0.6 / range 40 reads as a black void, 2 / 95 blows the walls to flat grey, and ~1.2 / 85 lands. Assert the FLOOR in the harness (so a later edit cannot re-darken the room), then confirm the look in a real client session — an unverified intensity change overshoots exactly as easily as it undershoots, and both look like "polish" in a diff.
- **Walking matters more than teleporting here too.** Assert that a tick in the tutorial area does NOT satisfy the "reached the main hub" step, so the step's condition is the one you meant, not "stood anywhere".
- **Prove each new assertion BITES before trusting it.** After fixing a defect, re-introduce the old behaviour and confirm the assertion fails, then restore. An assertion that passes both ways is decoration; mutation-checking it is the cheapest way to know the guard is real (verified rates: 4.79 vs 6.66 GP/tick, buried vs grounded collectible, crashed vs restarted loop).

## Headless simulation harness

Studio is unavailable or blocked, yet the game still has to be verified. Run the REAL server and client modules headlessly against a mock Roblox API instead of trusting lint. This is the strongest evidence available without a renderer, and it finds real bugs (nil-index resets, dead prompts, broken pacing) that `luau-lsp` cannot.

Shape: `tests/sim/{mock.luau, build.py, run.luau, client.luau}`.

1. `build.py` stages `src/{shared,server,client}` into `.sim/` (gitignored), rewriting instance requires to plain-Luau relative ones and injecting a prelude of locals, then appending `return true` to Script-type files. Assert the rewrite is TOTAL — abort if any `require(script` survives; a silently unrunnable module makes the sim lie.
2. `mock.luau` implements only the API the modules actually touch: Instance tree with dot-access children, signals, `Vector3`/`CFrame` arithmetic, stable `Enum` tokens, DataStore, MarketplaceService, CollectionService, TweenService, `BindableEvent`, and a deterministic `task` scheduler with `pump(seconds)`.
3. `run.luau` requires the staged Bootstrap (which boots every service for real) and drives `Request:InvokeServer(player, kind, payload)` exactly like a client. `client.luau` adds a `PlayerGui`-backed LocalPlayer, requires all client modules, and fires every panel button and keybind.

Full recipe, mock traps and assertion rules: `references/headless-simulation.md`. Generic staging script: `scripts/stage_sim.py`.

Boundary: this proves server/client LOGIC. It cannot see rendering, layout, touch input, physics, or streaming. Those rows need a real client — and Studio is not the only one: the browser client (below) renders the published place and accepts real keystrokes, so "no Studio" is not by itself a reason to leave a rendering row unverified.

**Re-run `build.py` after EVERY edit to `src/` or to the tests.** `.sim/` is a staged copy, so the suite runs against whatever was staged last: a failure that contradicts the code you just wrote usually means you are testing the previous module, and a green run can be passing against code you have since changed. Both directions of that lie are real — rebuild first, then trust the result.

## Browser-client playtest (when Studio will not start)

If the place is already published, `play.roblox.com` runs the real client in Chromium and gives you rendering, physics and input without Studio:

1. Open `https://play.roblox.com/games/start?placeId=<placeId>`. The place's own page is the wrong entry point — the owner account sees **Edit in Studio** where a Play button would be, so use the direct start URL.
2. A first attempt can fail with **Error 279** ("Failed to connect to the Game") while a server spins up. Reload once and let it sit; the loading overlay clears into the live render.
3. Size the window for QA (`Emulation.setDeviceMetricsOverride`), click the canvas to give it keyboard focus, then dispatch keys with `Input.dispatchKeyEvent` (`key` + `code` + `windowsVirtualKeyCode` + `text`). Those reach `UserInputService`, so panel keybinds and prompts fire exactly as they do for a player.
4. Read results with screenshots + vision, then cross-check every claimed defect against the source before acting. A prompt read as `[F]` when the code leaves `KeyboardKeyCode` at its `E` default is a vision misread, not a bug — vision gets text, layout and blank panels right and small glyph reading wrong.

## Route reachability (headless harness)

**Teleporting is a biased test.** Every assertion that calls `setPos(player, target)` proves the target exists, never that a player can REACH it — so ground holes, narrow bridges, floating pickups and unreachable prompts pass a green suite. Add a player's-eye pass that (a) samples the ground continuously along each real route at 4-6 stud intervals and fails on the first gap with its coordinates, (b) crosses the FULL width of a doorway/opening rather than its centre line, (c) checks every `ProximityPrompt`'s host part has ground beneath it and stands within the prompt's activation distance, and (d) asserts travel times at the default walk speed so a route cannot quietly become a two-minute hike. Sizing rule that follows from it: any connecting ground must be at least as wide as the opening it serves and as deep as the area it joins — a 40-stud path under an 80-stud arch leaves a void on both sides that only a walking player finds.

## UI layout audit without a renderer

A blocked Studio does not make layout unverifiable — the client modules can print their own geometry. Dump the
built ScreenGuis (every panel, label, button: design-space rect, colour, text, `TextWrapped`, `TextTruncate`),
render the rects to PNGs to look at, and audit the same JSON numerically as a gate. Full recipe, collector
rules and the audit's defect classes: `references/ui-layout-audit.md`.

Ship the audit as a durable gate with a ONE-LINE command in the project's docs, not as a throwaway probe — the
value is that every later edit re-runs it. Keep the dump and the audit as separate `tests/sim/` scripts so the
render-to-PNG step stays optional (looking) while the numeric check stays mandatory (passing).

What it catches that no runtime test does:

- **Text that cannot fit its box.** Roblox TextLabels do NOT ellipsize by default — an unwrapped full sentence
  in a fixed box is cut mid-word with no error and nothing in the log. Any label carrying prose from Config (an
  upgrade's `effectDesc`, a product description, a hint) needs `TextWrapped = true` plus height for two lines.
- **A panel larger than the design viewport, or a child positioned outside its panel's rect.**
- **Absolutely-positioned controls that overlap** — the edge toggle rail is the usual offender.
- **Touch targets under ~28px in design space**, invisible on desktop and unusable on a phone — and the same floor applies to TYPE: a 12px grey line on cream is unreadable both in a screenshot and in the game, so keep body text at 13px or more with real contrast against its own panel colour, not against the scene behind it.

Two rules that keep such a gate honest: `UIText` measurements must over-estimate (fail on the safe side), and
list-layout children must be excluded from overlap checks because their `Position` is `(0,0)` until Roblox
lays them out — a naive check reports a hundred "overlaps" on a clean layout. Prove the gate BITES by
injecting a clipped label and a 12px button into the dumped JSON, confirming failure, then restoring.

- **Pixel-probe a claimed visual state before acting on it.** A vision model will confidently report "no dim layer", "the rail is missing", or a "purple banner" that does not exist, and each false report costs a styling pass on working code. Sample the same screen region with and without the feature and compare channel means (a 50% scrim cut a 163-brightness floor to 90, which is the proof it renders); read the source when the claim is about behaviour. Vision is for text, layout gist and hierarchy, not for deciding whether a mechanism runs.

The rendered PNGs are a GEOMETRY view, not a content view: rows a client script generates at runtime (list
layout children, scrolling-frame contents, anything built after the dump) do not exist in the JSON, so every
panel can render as a large empty card while the live game shows it full. Never restyle a panel because the
contact sheet calls it "unfinished" or "empty" — confirm the emptiness in the live client first, and treat the
sheet as authoritative only for clipping, overlap and off-panel geometry, which is what it actually measures.

## UI surfaces: modern styling without recursion

Roblox ships the depth primitives natively (`UIShadow`, per-corner `UICorner`, `UIStroke`, `UIGradient`), so a modern surface is a corner + hairline stroke + soft shadow + a faint tint gradient — never a 9-slice image or a hand-rolled fake. Recipe, scrim, pop-on-open and the review loop: `references/ui-styling.md`.

- **Style centrally, once, at registration — never inside a click handler.** Creating a Frame or a modifier while a panel opens re-enters whichever descendant hook owns the UI pass; the observed failure is a silent process abort (suite `exit=1` with no assertion line printed), which reads like a broken harness rather than a bug in your code.
- **Guard idempotency with an ATTRIBUTE (`panel:SetAttribute("TgStyled", true)`), not `FindFirstChildOfClass`.** A class the engine or the sim harness does not register by name never matches the lookup, so the modifier is recreated on every pass forever. Name an instance BEFORE parenting it for the same reason: parented-but-unnamed is invisible to the guard.
- **Wrap the ordering pass in a reentrancy flag AND a `pcall`.** Without the flag, adding a modifier fires the descendant hook, which re-orders, which adds a modifier, until a C stack overflow. Without the pcall, one bad child leaves the flag stuck `true` and every later styling pass silently no-ops for the rest of the session — the UI just stops updating with no error.
- **A runtime-created Frame needs an explicit `Position`.** Unset, it reads as a number rather than a UDim2 and the next geometry pass dies with `attempt to index number with 'Scale'`.
- **Dim the world behind a modal.** A panel floating on a fully lit scene is the most reliable "prototype" verdict an independent reviewer will give you. One full-screen frame at ~0.55 transparency, sized `1,0,1,0`, with an explicit `Position`, created at startup and toggled on open/close, is most of the fix — but WHERE it is parented decides whether it renders at all. A ScreenGui's `DisplayOrder` decides stacking between guis, so a dim layer belongs in the gui that renders UNDER the panels (in this project the HUD is `DisplayOrder = 1`, every panel gui is `2`), not necessarily in the panel's own gui. Verify from a live capture that the world actually darkens; a backdrop that exists, is visible and still shows nothing has a stacking/parenting problem, not a transparency one.
- Judge the result from a live capture, not the offline renderer — see `## UI layout audit without a renderer` for why the contact sheet lies about content.
- **A verification cycle is a budget, and plumbing spends it.** Each visual change costs an inject → play → capture round trip, so when a styling pass and its harness plumbing compete for the same cycle, ship the visible change first and confirm it, THEN fix the plumbing. A run of turns that produces no new screenshot reads to the owner as no progress, however much code changed — and "I fixed the harness" is invisible in a game they are looking at.

## Monetization (developer products / game passes)

- `MarketplaceService.ProcessReceipt` is the ONLY purchase authority. Install it once from a server service; never grant from a client `PromptPurchaseFinished`.
- Grant, then persist the `PurchaseId` ledger, then `commit`/save, then return `PurchaseGranted`. Any failure returns `NotProcessedYet` so Roblox retries; a duplicate `PurchaseId` returns `PurchaseGranted` without paying twice.
- Validate `PlayerId`, product allowlist, player presence, and the `DataLoaded` attribute before touching data. Refuse unknown product IDs — those are placeholders, not errors to swallow.
- Ship with `id = 0` placeholders and a `configured = false` flag; zero IDs must never prompt and never grant. Game passes are read server-side (`UserOwnsGamePassAsync`) and refreshed on join, never trusted from the client.
- **Products and passes belong to ONE universe.** A developer product or game pass created under a different experience's universe never appears in the published game, and no dashboard view warns you. Confirm the LIVE universe first — `games.roblox.com/v1/games?universeIds=<id>` for the published experience, or the `[telemetryLog] universeid:` line in the running Studio's session log — then create everything under that universe. Re-creating three products is a cheap fix; discovering the shop is empty at launch because the IDs point at an abandoned placeholder experience is not.
- **Activation is a verified step, not a flag flip.** Fill real IDs only after reading them back from a public endpoint (`product-info` for passes, the developer-products list for products) and confirming price and on-sale state; then set `configured = true` and re-point the tests from placeholder-shaped assertions to real-ID assertions. A screenshot of a filled form is not proof a product exists. Recipe and endpoints: `references/publishing.md`.
- Cap the persisted receipt ledger (e.g. 64 entries, trimmed on migration) so a save cannot grow without bound; a boost-type product applies to BASE income only, never to the social/skill multiplier on top.
- **A sink shallower than one-time income makes the paid tier worthless.** If a premium currency has 18 one-time sources against 18 total spend, a player exhausts the entire shop in one session and the bundle you are selling buys nothing. Budget the sink depth (and its tiers) against both one-time and recurring income before pricing anything, and assert it: total sink > all one-time income, and the earnable ladder is tens of hours rather than minutes.
- **Never open the shop on the most expensive item.** An unsorted cosmetic list whose first row is a 100,000 GP crown reads as "nothing here is for me". Sort cheapest-first within currency (earnable currency first, since every player has some) and show a rising ladder across sessions.
- **When the player cannot afford the premium currency, give them the route.** A dead disabled button is a lost sale and a confusing dead end; turning it into "Get NT" that opens the Robux panel is the whole conversion path. Do not rely on a keybind for the store — nobody discovers it.

## Publishing and going live

Creator Hub has **no place-file upload**. The published place changes only via Studio's Publish or the Open Cloud versions endpoint, so a workspace can be green on every local gate and still serve its default baseplate. Two gates precede either path: the content maturity questionnaire (until it is submitted the overview reads "Game unplayable") and real Creator Hub product IDs. Endpoint, required scope, 401-vs-403 diagnosis, API-key capture traps and Creator Hub automation notes: `references/publishing.md`. Pushing a source-tree fix into an ALREADY-published place (`write_script` → read-back assertion → Publish → `updated` timestamp, and why the live place then only partially matches HEAD): `references/studio-mcp-linux.md`.

- **Publishing does not exit play mode.** Studio keeps running the session after File → Publish, so a following `F5` is a no-op and any capture you take comes from the OLD server — you will judge, and possibly "fix", a frame that predates your change. Always `shift+F5` first, then inject, then `F5`. Entering play mode also kills the bridge plugin's polling session, so the cloud place's client id goes stale and `write_script` jobs time out while another Studio window answers as client `0`: stop play, confirm the intended client id responds, then inject.
- **Prove WHICH session you are about to publish from.** Run `run_code 'return tostring(game.PlaceId)'` in the Studio you are driving: a real id means that window is bound to the cloud place and File → Publish updates the live game; `0` means it opened a local `.rbxlx`, whose publish flow only creates a NEW experience (its "Update existing experience..." link is inert under Wine, so there is no post-hoc way to retarget the file). Two Studio windows open at once is the usual cause — the local-file one registers as bridge client `0` and answers the jobs meant for the cloud session. Check the id, not the window title.

- **A temporary QA script is how you reach a spot during a play session.** Play mode kills the bridge, so nothing outside can reposition the character; instead, in EDIT mode, create a named `QA_*` Script in `ServerScriptService` with `run_code` (`Instance.new("Script")` + `.Source` + parent — `write_script` fails with `Instance not found` for an instance that does not exist yet) that loops the character to the target, play, capture, then DESTROY it before publishing. Forgetting the destroy ships a teleport into the live game. Give it a one-second re-assert loop rather than a single `CharacterAdded` hop, or a slow server leaves the player at spawn.
- **Trust `/clients`, not the plugin panel's status label.** The panel can read `running (connected)` while `GET 127.0.0.1:28650/clients` reports that id `connected:false` with a stale `last_seen`; jobs sent to a dead id time out with nothing but `timeout` to go on.

The rule that survives all of it: **verify liveness from outside your own session.** `games.roblox.com/v1/games?universeIds=<id>` returns the live name and `updated` timestamp, so if `updated` predates your build then nothing you built is published regardless of what any flow reported; `apis.roblox.com/game-passes/v1/game-passes/<id>/product-info` returns `PriceInRobux`/`IsForSale`. Read those before making any publish or monetization claim.

### Diagnosing a Studio-on-Wine version regression

When a Studio build that previously ran fine starts crashing at startup after an update, the fault is almost always window creation, NOT your place. Reproduce first with NO place open (`Studio --help` or an empty launch): if it still crashes, your game is exonerated and you are debugging Studio+Wine, not Luau.

Name the cause by COUNTING the signal across the WORKING version's session logs before trusting any warning in the failing log. A warning that also appears in healthy sessions is pre-existing noise, not the fault; only a line that is ABSENT from every working log and present in the crashing build is the differentiating signal. Concretely: Wine's `EnableNonClientDpiScaling() ... (Call not implemented.)` warning appears in every working session and is NOT the cause, while `WindowCreationData::create: CreateWindowEx failed` (leading to `RBXCRASH: win ID is 0`) appears zero times in working logs and only in the crashing build. Do not pin the nearest visible warning as the cause before you have counted it across the working set — that over-claim has to be walked back. Test each hypothesis (GPU/driver, Wine build, Flatpak sandbox vs direct, Qt high-DPI env overrides, virtual-desktop registry) against a no-place launch and record pass/fail for each.

**Use a control app to separate the launcher from the app.** Launch something trivial (Wine's own notepad) through the exact same launcher path and prefix. If notepad ALSO fails to create a window (`nodrv_CreateWindow`, `egl: failed to create dri2 screen`), the fault is the sandbox or the GPU plumbing and no Studio build will run there — stop testing Studio versions and fix the launcher. If notepad opens, the sandbox is fine and the crash is genuinely version-specific. This split is what turns a weeks-old "Studio is broken" report into an actionable finding, and it is two minutes of work. When the exact failing API or window flag cannot be identified, say so honestly and leave the row as an external blocker rather than inventing a mechanism.

The transferable method: when two tool versions behave differently, diff the SIGNAL COUNTS across the working set before naming a cause — the differentiating line, not the loudest line, is the bug.
