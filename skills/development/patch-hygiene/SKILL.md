# Patch Hygiene

Batched patch-based edits fail silently more often than loudly. This skill governs the edit step itself: where anchors come from, how results are checked, and what proves an edit landed. When the edit's landing surface is a deployed site, `references/verify-shipped-change.md` extends that proof to the live bundle.

## Rules

1. **Anchors come from a fresh read in this turn, and are unique via distinctive plain context, not raw length.** old_string text must come from a read_file/search_files result produced in the current turn — never from remembered file content or a context-compaction summary. Summaries can carry excerpts from a SIBLING project with the same file names, and those read exactly like your target while matching nothing. This includes files you wrote earlier in the SAME session: the on-disk formatting (wrapped attributes, indentation, quote style, escape escaping) is not what you remember writing. If an anchor feels familiar, re-read the file first. Prefer an anchor that is a plain, distinctive statement line over a longer one that spans escape-heavy code (regex literals, template syntax, JSX attribute wrapping) — remembered escaping diverges at the backslash layer and phantom-mismatches while the plain neighboring line matches fine. A short fragment next to a lookalike statement is equally wrong: it lets the fuzzy matcher rewrite the NEIGHBOR line and still report success.
2. **Every edit call's result is checked — `success: true` is not `did the right thing`.** `hermes_tools.patch` returns `{success: False, ...}` instead of raising. A script that fires N patches and prints a closing line reports fiction. Assert every result (or collect them and fail on any `success: false`) inside the batch, AND read the returned diff: every hunk must sit where you intended. A hunk at an unexpected line means the fuzzy matcher hit a lookalike — repair it before doing anything else; never build later steps on a corrupted file. This includes programmatic `str.replace()` / `sed -i`, where a non-matching anchor is a SILENT NO-OP that still exits 0 and the script prints "done" regardless: after every such call grep for the NEW marker in the file (and before writing any commit message that names the change), so a message never claims an edit that is absent from the diff.
3. **The diff is proof the edit landed.** After a batch, `git diff --stat` (or a re-read of the touched spans) must show the expected files/hunks BEFORE any "patched" / "updated" claim. Narrating the intent of an edit is not evidence it applied.
4. **Multi-file mechanical batches are transactional: verify everything before the first write.** Build all replacements from disk reads in one script, count-verify every anchor, and abort before the first write if any count misses. A half-applied batch is harder to fix than the original state, and a lone `patch` call per edit cannot roll back what already landed. Run assert-per-replacement batches as two passes over the same replacement list (pass 1 asserts every anchor exists, pass 2 applies and writes): a lazy batch that asserts while replacing and fails on the LAST anchor discards the already-computed replacements and burns a full re-run. When a batch dies on one missing anchor, do not re-run it blind — the miss means your memory of that code REGION is wrong, so re-read the region from disk and treat every remembered anchor in it as suspect before re-running the rest verbatim.

5. **Edits you did not make (killed subagent, aborted batch, resumed work) get a syntax parse before anything else.** Sweep every touched file with the language's fastest single-file checker (JSX: `npx esbuild <file> --loader:.jsx=jsx --outfile=/dev/null`; JS: `node --check`) so all broken files surface in one pass instead of fixing one full-build error at a time. A syntax error pointing at a LATER line ("Expected X but found Y") is an unclosed delimiter EARLIER — scan open/close pairs between the last good region and the error line, including JSX comments (`{/* */}` needs its closing `}`) and half-finished tag renames (`<header>` closed by `</div>`). Crude grep tag counts cannot diagnose this — strings and comments skew them; the parser is the only arbiter.

## Pitfalls

- `replace_all` anchored on a VARIANT span replaces only the lines carrying it. Near-identical twins (`X_OPTS.map(<option …>)` vs `Y_OPTS.map(<option …>)`) differ only in a prefix; if that difference sits inside old_string, the second twin silently survives while the diff looks complete and the old text keeps rendering. Count the intended hits first (`grep -c` expects N), anchor replace_all on the span the twins truly share, and grep the OLD pattern to zero afterwards before claiming the change landed.
- A fire-and-forget patch loop "succeeds" N times while writing nothing; the failure only surfaces later when dependent steps read stale code and every symptom points somewhere else, so the debug trail starts from the wrong end.
- Never chain sequential find→replace rules whose output can match a later rule's input (remap 11→13, then 13→16, and every original 11 silently becomes 16). Remap many values (sizes, ids, names) in ONE pass with a mapping table (`perl -pi -e 's/pat/map{$1}/ge'` style) so each source value is replaced exactly once; count matches and diff before building.
- Git-untracked or freshly written files produce empty `git diff` output — prove those with a re-read or `git status`, not diff.
- When a patch is refused with a "similar but different text" error, the error's quoted section IS the file's live state and may contradict your earlier read. The "Did you mean" hint lines quote the exact live text: copy one verbatim as the new old_string (old + suggested line) instead of re-guessing whitespace or wrapping, and diff-check the result.
- A patch is REPLACEMENT, never insertion: everything in old_string is deleted and new_string is the entire replacement. When inserting at an anchor, old_string must be ONLY the anchor — every extra line it absorbs (a neighboring comment, blank line, next statement) silently disappears unless new_string reproduces it verbatim. The returned diff catching a dropped line is the last line of defense, not the plan.
- A patch that replaces only part of a line must keep the line's closing delimiter in BOTH strings. When old_string covers a JSX/attribute span but the line ends in `>` or `/>`, dropping that trailing token from new_string leaves a stray `>` in the file and the build breaks on a line that "looks patched"; include the full line in both strings, or run the build/lint immediately after the batch.
- A splice that REMOVES a JSX branch (ternary, `&&`) or WRAPS a block in a new container moves delimiter ownership: the removed branch strands its trailing `)}`, and the wrapper's new closes land in the splice's tail where they look plausible. The parse error surfaces many lines BELOW the damage. Parse (single-file esbuild check) after EACH structural splice, not after the whole batch, and read the first lines after the splice point against the pre-splice tail — every close there must have a live opener.
- Two failed anchors on text you are sure is present is a wrong-content signal, not fuzzy-matcher flakiness: stop varying the anchor, re-read the whole file, and if it is small, switch to ONE verified full rewrite (`write_file`) after that fresh full read instead of a third anchor guess. Anchors reconstructed from a context-compaction summary or from your own earlier prose routinely diverge from disk (sibling projects, drifted versions, formatting you misremember), and each retry against phantom content wastes a turn.

- Do not build edits inside an `execute_code` heredoc or a triple-quoted Python string. Nested heredocs (`<<'PY'` containing `<<'EOF'` or a `"""` literal) and unbalanced quotes make the WHOLE cell fail with a SyntaxError before anything runs, and regex metacharacters inside it emit escape warnings that mask the real break. Prefer the `patch` tool for targeted edits and `write_file` for new files; if a scripted batch is genuinely needed, keep it to one flat `python3 -c` / `python3 <<'PY'` level with no nested quoting and assert every result. WHY: the failure is at parse time, so zero edits land while the transcript shows a plausible code block that never executed.
- An oversized tool batch executes NOTHING: several multi-KB `write_file` payloads (new source files) in ONE turn can stall the delivery stream before any call runs, so the batch vanishes without a result and none of the files exist afterwards. Generate large files one per turn or in sections (skeleton `write_file`, then `patch` appends), and when a batch stalls do NOT resend the same payload — split it before retrying. Verify with a marker grep as for any refused call.
- A refused or aborted tool call executes NOTHING — including every write its script contained. Tool-level refusals (a command that looks like a long-lived server/watch process, a blocked pattern) and mid-script crashes both leave zero side effects while the transcript still shows the full intended code block. After any refused or non-zero call, grep for the marker of EVERY write it contained before believing any of it landed; the tell is a later probe crashing on a helper "that was just added". Specific durable case: `npx vite build` / `webpack`-style build commands trip the terminal tool's long-lived-process guard when run in the foreground — run them with `background: true` redirecting to a log, then read the log in a later call. A refused foreground call containing BOTH edits and a build silently loses the edits too.

- A diff hunk whose old and new lines LOOK identical means a character-level difference you cannot see: a dropped trailing delimiter or an invisible codepoint. Dump both with a repr/codepoint compare instead of your eyes; if the file still fails to parse with no visible culprit, rebuild the file from HEAD plus one replacement at a time and parse after each — the step that breaks names the corrupting edit.
- A supersession edit can land cleanly while leaving the fix inert: a corrected binding (`effectiveX`, `newFlag`) at the definition site does nothing while a consuming call site still passes the old identifier — the diff looks right and old behavior silently persists. After any rename — identifier or display string — grep the superseded name and expect ZERO references before claiming the fix, and sweep the full carrier set: code call sites, display metadata (document title, PWA manifest name/short_name, platform title meta tags, notification fallback titles), mock/seed default rows, and the QA/test tree. Test fixtures that SET the old value (rename-and-revert tests) and assertions that EXPECT it go stale silently; a suite that passes proves nothing when its own fixture writes the old string back.
- Do not patch the control the user's word suggests when the code shows something else: before patching a described UI difference ("page X lacks the Y that page Z has"), diff the compared views in source first. User widget vocabulary is approximate (a segmented tab pill may be called a "slider"), and patching the imagined control leaves the real gap in place; extract a shared component both views use rather than re-creating the control in one place.
- Tooling corrupts secret VALUES in BOTH directions, so never design a step that needs the agent to hold one. (a) OUTPUT: rendered tool results mask secrets — a template like `Bearer ${KEY}` comes back with the interpolation replaced by `***`, and that mask is what a copy-pasted anchor or new_string writes into the file (literal `***` where `${KEY}` belonged), breaking at the first request or at the `${` syntax. (b) INPUT: a real secret written into a file or command is TRUNCATED at write time (a 49-char key lands as ~18 chars), so `curl -H "API-Key: <key>"` and probe scripts silently carry a short bogus value and fail auth. Reconstruct auth/header/token SYNTAX from source structure, never from rendered output or a remembered value; and route the secret VALUE through the environment, not through the agent: write code that reads `process.env.X`, have the user paste the value into the provider dashboard / Vercel env, and probe a remote API from a DEPLOYED function that already holds the key instead of a local curl. After editing any auth/header/token-bearing line run the language's syntax check (`node --check`) — it names the corrupted line even when the mask grep is skipped.

- A generator that rewrites a REGION of a file must anchor on that region's FIRST line, and must be run twice before you trust it. Anchoring on the region's last line (`Config.Meshes = {`) leaves the comment header above it untouched, so every run stacks another copy of the header — and a `--check` mode that compares the file against freshly generated output then reports 'stale' forever, which is how a generated-file check becomes noise everybody skips. Anchor on the first line of the region, assert the block still occurs exactly once after regeneration, and prove idempotency by running the generator twice and diffing to zero.
- A scripted `text[:i] + replacement` splice anchors `i` with find() on a heading or marker line: when that marker sits at or near end-of-file, the splice silently deletes the entire tail after it (conclusion, references, closing sections) while content-level check gates stay green — they never asserted the tail. After a batch of splices on a generated source document, assert structural completeness first (every expected section header present exactly once, the final expected block present) before regenerating downstream artifacts.
- Run global find-replace cascades (number migrations, renames) in their own pass BEFORE targeted replaces whose anchors contain the replaced text: the cascade rewrites the exact strings later anchors are built from, so post-cascade anchors MISS against pre-cascade strings. Derive targeted anchors by reading the post-cascade file.

## Key pattern

```
✅ read → patch with anchors from that read → check each result → git diff --stat matches expected files → claim
❌ batch-fire patches with a hardcoded success message
```
