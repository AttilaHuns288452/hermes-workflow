# Cost-Benefit & Business Case Documents

Covers CBAs, pricing build-ups, TCO, and feasibility-based business case documents built from source studies. The deliverable is ONE polished academic document (DOCX + PDF) of the analysis itself, not a supporting package. Every number in it is model-generated and verified; the document must survive hostile panel questions (defensible, in-depth, no holes).

## When to Use

Trigger conditions: the user asks for a cost-benefit analysis, CBA, pricing build-up, total-cost-of-ownership study, feasibility-based business case, or a financial defense/panel document built from study source docs. Also use when polishing any analytical report to match a provided reference document's formatting identity, or when validating a financial document's numbers end to end.

## Procedure

### 1. Ingest source truth
- Prefer the user's provided Google-Docs `.docx.md` exports over python-docx extraction whenever tables matter — body-level python-docx iteration misses tables inside content controls. Reconcile exports against the docx when in doubt.
- Build an inputs register before modeling: each input with its source file, the conflicts between sources (table vs prose), and explicit gaps. This register is the audit trail the document's assumptions cite.
- Extract the reference document's visual identity first when one is given (see Standing preferences): render its pages and read its styles XML (fonts, colors, margins, table grid/shading, caption and footer treatment).

### 2. Reproducible model layer (single source of truth)
- One Python script recomputes every published figure: BOM roll-ups, unit costs, cloud/infra cost ladders, tax, ROI, payback, sensitivity cases. Assert each recomputed figure against the source docs' published numbers — a published number you cannot reproduce is a finding, not a rounding.
- Prose numbers are GENERATED from this model. Hand-computed copies inside prose tables are the #1 defect class independent reviewers catch (copy errors, factors of 2, wrong sensitivity bases).
- Keep the model's own output dump (machine-readable) so document generation and later audits read the same values.

### 3. Formula workbook
- Build the Excel workbook with live formulas (openpyxl). openpyxl writes NO cached values, so verify by converting a copy through `soffice --convert-to xlsx` and asserting every CHECK row computes 0 and totals match the model.

### 4. Author the document
- Sections as markdown, then convert. Dense prose becomes tables wherever content is structured (see Standing preferences).
- Credit benefits, harms, and costs to the perspective that bears them (developer vs customer vs community); label cash vs economic costs (unpaid labor is economic, not cash).
- Pricing build-ups: cost base + explicit markup, with per-volume columns and memo rows for TOTALS, so readers can see totals rise with volume while per-unit fixed shares fall. Never claim volume discounts without quotes.

### 5. Polish to reference style
- Use the pandoc + python-docx pipeline (title page, TOC with real page numbers, footer fields, numbered table captions, full-grid shaded tables, reference-style typography). Recipe and its pitfalls: `references/docx-polish-pipeline.md`.
- When tables or headline numbers change in the markdown, update the pipeline's table-fingerprint list and figure-check strings in the same pass.

### 6. Independent review before sign-off
- Two layers: (a) an adversarial reviewer subagent that hunts for holes (unsupported claims, arithmetic, missing assumptions), (b) a second-path verifier script that recomputes the money math from raw inputs with its own code and reconciles the DOCX tables against the model output. Finish the edit pass and freeze the file BEFORE spawning the reviewers: audits launched against a mid-edit document report findings the later edits already superseded, and triaging phantom findings costs more than the wait.
- Validate every reviewer finding against the model BEFORE patching and against the LIVE FILE text for presence; then fix at the owning layer (model or document source) and regenerate — never patch a number in prose alone. Reviewer registers (especially multi-round "loop again" audits) are often captured against a mid-edit dump: findings may name defects that are already gone or omit ones the edits introduced, so triage each finding against the current file and rerun a consistency sweep after every fix round.
- After fixes, rerun the full chain (model asserts, workbook recalc, polish checks, verifier) and merge findings + dispositions into a QC report.

### 7. Verify
- Programmatic: table count and fingerprints, caption count, TOC page numbers vs FINAL pagination (remap after any layout change), figure strings present, no leftover internal tokens in the body.
- Programmatic scans before vision: a forbidden-string sweep (every removed item counts 0) and a per-table "Source:"-line audit catch content regressions cheaper than any visual pass.
- Visual: render the PDF and inspect the densest pages (long tables, sensitivity, references), asking concrete per-page questions (mid-word breaks, misleading zero-price cells, header weight, cramped columns) — pointed questions return actionable layout findings. Confirm any vision-flagged defect against ground truth (PDF text extraction / docx XML / bounding boxes) before editing — vision frequently reports defects that are not there.

### When the user hands back an edited file
The file the user attaches ("this is now the file") IS the source of truth from that moment — their edits and formatting win, even over your own last build. Switch from regeneration to in-place editing: dump its tables (index, shape, header row) and caption list first to map its structure, back it up (`backup_<name>.docx` beside it), then apply changes with python-docx surgical edits (see docx skill, "Table surgery in place") preserving their styling. Never re-run the generation pipeline over their file — it discards their edits.

### Recalculation pass (when the source study is revised)
When the truth document is revised and the analysis must be recalculated, the DOCUMENT TEMPLATE IS FROZEN: structure, section order, table shapes and prose style stay exactly as they are; only values and the sentences that state them change. Sequence:
1. Extract the revised document's own money tables and diff them against the model's inputs before touching anything — that diff is the change list, and it separates real changes from reinterpretations.
2. Rewrite the model to the new truth in one pass and assert against the new published aggregates (the revised study's own case totals, break-evens, budgets), same standard as step 2.
3. Update the document in passes, cheapest first: global scalar swaps (old figure -> new figure) in ONE mapping pass, then rebuild changed tables straight from the model's JSON dump, then narrative sentences and "Arithmetic:" lines. Re-grep the current file text before deriving each later pass's anchors — earlier passes rewrite the strings later anchors are built from (see patch-hygiene). Grep every superseded figure string to zero at the end.
4. Regenerate through the polish pipeline (update the table-fingerprint list and figure-check strings when table shapes changed) and sync every derived artifact (workbook, defense Q&A) from the same JSON — a recalculated CBA with a stale workbook is an internal-consistency finding.

## Standing user preferences (always-on)
- Final deliverable = the polished document itself (DOCX + PDF). Copies go to BOTH `~/Downloads` and the project root, with a README pointer saying what it is and how to open it.
- Body prose is plain language: NO ID/code tokens (G-07, R-12, GAP-001) in the body — traceability IDs live only in appendix registers. Tables over prose blocks for structured content. No special typographic characters (em dashes etc.); readable sentences over jargon.
- The document reads as a formal deliverable at all times: no informal approximations in prose or cells ("about 700" for 700 — hedged round numbers read as sloppy) and NO inline draft or verification tags ("[CHECK: ...]", "TODO", "TBD") anywhere in the body — pending verifications live in one clean labeled list or appendix section. Draft markers left in a "finished" document are the first thing that reads unprofessional.
- When the user provides a reference document, match its visual identity exactly (compare the corresponding pages first, then restyle) — this applies to documents, not just UI.
- Cost base = cash the venture actually pays (hardware materials incl. PCB/packaging, delivery, warranty allowance, platform/payment fees, cloud services, operating costs). Imputed labor is NOT a cost when the team does the work and nobody pays for it (standing user direction): exclude development AND assembly labor from every computation and say why in one note beside the per-unit cost breakdown ("no labor is costed anywhere; the team's compensation is the markup"); if assembly is later outsourced, note the per-unit add it would create. A made-up rate times estimated hours is the first number a panel attacks. Real cash development spend (prototype budget, bought services) is ONE-TIME: split one-time work by lifecycle component (app development vs firmware/hardware development) and state each component's recurrence explicitly ("built once, included free with every unit: no recurring development cost") — a lumped development line reads as recurring to a panel. Excluded estimates may appear only as labeled memo tables marked "for viewing, not included in the computations", never feeding a total or computation. Free service tiers are acceptable at low scale.
- "Loop and verify" means: iterate QA passes on the deliverable itself, fix confirmed defects at the owning layer, repeat until clean. A passing build check is not the finish line.
- For graded/defense documents: every claim must be traceable to a source; unprovable claims are labeled as such. Documents must be cross-consistent (same IDs, names, figures across files).
- Every number is justifiable IN the document, in three layers: inline author-date paren cites in APA style (e.g. (Proponents of MoldGuard, 2026a; Manila Electric Company, 2026)) on load-bearing sentences, a "Source:" line under EVERY table (naming source documents by author and year), and an "Arithmetic:" line showing the exact formula for each computed figure (e.g. `6,190.07 - 249.55 - 275 + 879.92 = 5,745.92`). A figure with no visible trail is a defect. Never ship bare [n] numeric cites; convert them to author-date as the final authoring step.
- Prices are single values. Ranges in price/cost tables read as unexamined; a band is allowed only when the row is explicitly a scenario (harm bands, not prices).
- The service/infrastructure stack in the cost model must be exactly the services the project proposal names — cheaper generic substitutes (a VPS instead of the named PaaS, a cache nobody proposed) are defects even when the math works. A cheaper alternative may appear only as a labeled contingency ("not part of the proposal") with an explicit adoption trigger; the base case and the simulation never depend on it, and it is never framed as a replacement of the proposal's product — "replaces X" reads as a deviation from the approved proposal and becomes a panel attack. When an earlier variant is corrected out, name its removal in the consistency table so deltas stay traceable.
- One-time product prices must pre-fund recurring per-unit costs: show the per-unit reserve (fleet five-year recurring / devices) with a covered/not-covered verdict per scale, and size the price to sit inside the survey's most-selected price band.
- The per-unit story gets ONE waterfall table ("everything the business pays per device") with tier-scenario columns (e.g. free-tier vs paid-tier cloud): hardware / delivery+warranty+fees / cloud / ongoing (marketing, taxes) → total cost per unit → markup → net profit after tax → final selling price, arithmetic per row. The multi-year simulation runs the same tier scenarios as separate tables, each carrying ROI on the development budget and payback; sales volume is stated at team build capability with a factory-scaling caveat (more units per year, lower parts cost at volume) — never an unexplained volume number.
- Customer-side analysis has a fixed shape: a with/without comparison in three columns (do nothing | manual alternative | the product) with problem-cost lines drawn from the survey's own spending bands (band midpoints, weighted-average arithmetic shown; the effectiveness assumption — halving, full avoidance, or a measured rate — named wherever it drives a number, never a silent hedge), plus a verdict table organized by survey band whose rows are computed as with (cost of ownership + residual spending after the assumed device effect) versus without (gross problem spending) and cover 100% of respondents (merge majority bands, show counts). Carry the value-premise note with the verdict: the device has value only insofar as it prevents the damage the survey measures; if it prevents nothing there is no monetary value. A gross-spending-vs-cost comparison is mathematically false (it ignores residual spending and the cost side) and is the first thing a hostile panel breaks. Claim "value-positive" only where the with/without math supports it; otherwise state the honest net, the break-even device effectiveness or quantity (net = effect x spending - cost of ownership), and what the gap buys (monitoring, alerts, automatic control). Add a scenario matrix (baseline utilization cost x survey spending brackets) showing each bracket's net benefit in context of the cost of ownership.
- Documents titled CBA carry discounted measures even when the headline figures are undiscounted nominal sums: an NPV at a labeled discount rate plus two more rates as sensitivity, and a benefit-cost ratio. ROI rows state their formula in the row label, and the working capital the plan needs (inventory cash) is disclosed beside the ROI and scenario-tested (sell-through), never hidden inside a near-zero investment denominator.
- When the mission is hostile-panel hardening, the deliverable set expands to: the final CBA (DOCX + PDF), the formula workbook, a defense Q&A (per question: a direct 1-3 sentence answer, the calculation, the source, and the CBA section carrying it), and a short audit report (what was verified, defects found and fixed, remaining limitations). When an audit question exposes a real weakness, fix the document itself (model, tables, framing) — a verbal defense is not the fix.
- When a source study is revised mid-mission, retain the existing document template and update values in place — the user stops rewrites with "retain our template and only update the prices". If the revision restructures a cost (an excluded allowance becomes a priced line), update the derivation, the exclusion notes and the risk rows together so the document never prices an item it also declares excluded.
- When a concept is removed from the document, delete it ENTIRELY — including sentences that announce its absence ("There is no X in this analysis"). Absence statements are clutter; the finished document simply does not contain the topic, tables and notes included.
- When the user says "make it like <reference document>" for reading experience, copy the reference's PRESENTATION HABITS ONLY (plain-language section openings, bold total sentences after tables, difference-column arithmetic, headline-first ordering) — never its skeleton or reduced scope. Replacing the full analysis with the reference's thin template reads as throwing the depth away.
- Conclusion and Recommendation sections are SHORT INSIGHT LINES, not prose blocks (user correction: "too blocky too many words, summarize it — basically the insight"): a bold Insights label with 2-4 one-line plain-language insights (who benefits, how the benefit scales with the customer's problem size, when the product is NOT worth buying, when the business case strengthens), then a Recommendations label with 3-4 one-line imperatives. A paragraph-per-theme conclusion gets rewritten to this shape on every pass.
- Mid-mission factual questions about the model get a direct answer and stop: report the figure and its derivation, and do not launch document changes until asked.
- The document is framed positively and easy to read (user goal: clean, organized, panelists don't have to nitpick) — never at the cost of honesty:
  - A build-up table with negative values (e.g. markup at certain fleet sizes) is a FRAMING defect even when the arithmetic is right. Keep the honest row but relabel it to name the scenario causing the negative ("Markup on the full proposal stack"), and add directly beneath it the positive-path row showing the mitigation's values at every scale ("Markup with the broker contingency"). The reader must see a positive route at every column.
  - Verdict/benefit tables are ordered HEADLINE FIRST: the target segment's row (the case where the product is clearly value-positive) is row 1, low-value rows last. Never call a small band "the majority" to strengthen the story — correct the misbelief in the reply and frame the band as the target segment instead. Numeric band rows (survey brackets, damage levels) are sorted by magnitude in reader logic (heaviest first for benefit tables) — never left in insertion order; rows added around existing ones must be explicitly re-sorted, because insertion at a fixed index places them in reverse and the panel asks "why is it 15 20 10".
  - Consolidate overlapping money tables: one source-data table plus ONE net-benefit verdict table. Three tables computing the same idea from different angles is sprawl the user will order deleted.
  - Headline tables assume FULL device effectiveness (upper-bound avoidance); a hedged effectiveness rate belongs only in sensitivity. When directed to assume 100%, purge every half-rate label and value from tables and prose.
  - A cost line whose cost is already carried by another line (upkeep = the electricity line) gets DELETED from the table; totals are unchanged because its value was zero or redundant.

## Pitfalls
- Index-based caption/TOC insertion lands on stale indices after ANY markdown restructuring — use cursor-based (order-aware) block matching, and keep a table fingerprint list (first cell of each table) validated per run; a removed table and an added table can keep the count unchanged and hide both changes.
- Horizontal-rule cleanup regexes ending in `\s*$` swallow the following newline and shrink the line array, so later insertions misfire. Preserve line breaks when stripping rules.
- Vision prose misreads: tight right-aligned numeric columns as broken text, substituted serif fonts as wrong-font, and phantom cross-reference typos (OCR noise on non-breaking hyphens). Verify every visual defect claim against extracted text/XML before "fixing" correct content.
- A document heading that inherits Normal's justify alignment stretches wrapped words one-per-line (all lines but the last get justified). Set heading styles to left-aligned explicitly.
- Extreme ROI on near-zero cash investment (student capstone) reads as an arithmetic error — lead with cumulative profit and payback, and caveat the percentage explicitly.
- Markdown rewrite ordering: section splices BEFORE token rewriting (splice anchors contain the tokens); reference renumbering BEFORE token stripping. Citation-format conversion (numeric [n] → author-date) goes LAST, after every content patch — it rewrites the exact text later patches anchor on; re-derive anchors from disk after any bulk text transform.
- Page-count floors in the check script must be set from a clean run of the current layout; compact tables legitimately reduce page count and a stale floor false-fails.
- Per-unit costs falling with volume is correct economics (fixed costs spread); a reader will read it as a bug unless memo rows show totals rising with volume alongside the per-unit fall.
- Every cost-base line item must match a source-BOM line by name — a cost line naming a component the BOM never prices (an unquoted board, a phantom part) inflates the base and becomes a panel attack. Reconcile line names; excluded allowances live as exclusion notes, never cost rows.
- A paid-tier row showing price 0 reads as "that tier is free" — put the real price with "not budgeted" in the condition cell, or write "not needed at modeled scale". Every component of a recommended option must appear as a row in the pricing table, including the alternative service that replaces a listed product, or its arithmetic cannot be verified from the table alone.
- Verify each load-bearing figure EXISTS in the named truth document (search the extracted text for the value) before shipping it — figures remembered or inherited from supporting documents drift, and a value absent from the named source is a defect even when the cite looks right. Supporting-document figures carry a labeled provenance line of their own, never the primary source's citation.
- A fee or allowance rate baked into the cost base must name where its rate comes from (the study's own table) and benchmark it against real-world provider rates with cites, saying which way it errs — an uncited fee percentage is the first number a panel attacks.
- In multi-year tables a hand-entered derived column drifts from the model even when the totals row is right (one column copied from the model, a sibling typed by hand). Generate every derived column from the model and assert each column sums to its totals row; when rounding breaks the sum by a unit, state "rows are rounded; totals computed on unrounded values".
- Free-tier claims are timeline and fleet-size claims. A zero-cost line backed by a free tier must be checked against the model's own calendar (tier EOL dates) and against fleet size at every modeled scale (device, connection and storage limits): if the always-on component's free tier cannot hold device connections, charge its paid tier from day one and let the other services ride their free windows. A pilot-year zero contradicted by provider notes in the same document is a critical finding.
- One-time revenue funding a multi-year service promise must show the tail: quantify each cohort's service years beyond the simulation horizon against the per-device reserves collected, label the horizon cutoff as a presentation choice, and state the promise's end date (e.g. five years from purchase). Booking full price while truncating the obligations is the horizon attack.
- Every printed "Arithmetic:" line must re-evaluate to its printed result exactly as written. A derivation that omits a term that IS inside the value (an old fee not removed, an allowance not swapped) reads as fabricated even when the final value is right; when the value is reachable two ways (source expected-case route and parts rollup route), print both routes and show they agree.
- Group and subtotal tables are summed from the item rows in the same document, never copied from a source study's table (the source may hold a different scenario's values, e.g. a discounted case). Assert the group rows sum to the printed total.
- After any model change, grep every superseded figure string to zero across the document before regenerating: contradictory values for one figure in two sections is the top internal-consistency finding hostile reviewers report. Content gates stay green through structural damage, so also assert every expected section header exists exactly once and the conclusion/references tail is intact before shipping.
- An excluded cost that law imposes regardless (implied warranty, mandatory certification) gets a quantified risk-register row with per-unit and total exposure, not only a disclosure sentence: keep it out of the price build-up when directed, but never out of the risk picture.
- Staged cash (pilot hardware, prototype budget, working capital) is counted exactly once across a simulation — either in the opening investment or in a flow row, never both. The ROI denominator may legitimately name total cash at risk while the flows show each item once; counting one item twice inflates the loss year and silently shifts payback. A pilot or build phase the study defines as not-yet-sales is cost in the simulation, never revenue.
- A loss year shows income tax 0 with the loss carried forward against later profit. A negative tax cell reads as an arithmetic error and is the first thing a panel questions.
- Survey band tables put COUNTS in the respondents column ("16 of 104"), not shares, and never a mixed share/count cell; when two averaging bases exist (all respondents vs positive spenders), print both as separate labeled rows, each naming its base in the ROW LABEL with the count in the counts column ("88 (84.6% of all respondents)") — never repurpose the counts column for a share note. Verdict tables group bands so rows cover 100% of respondents — a table that adds up to 85% invites "what about the rest".
