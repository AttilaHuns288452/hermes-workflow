# Universal Software Engineering

Method for engineering production-grade systems in any stack or domain. **Composable:** this skill carries the generic method; the project-specific skill carries schema, routes, business rules, and constraints. Load both — never let this skill overwrite project business rules, and never let project habits replace this discipline.

Depth on demand: `references/production-domains.md` (domain checklists). Live self-check: `bash scripts/verify.sh`.

## Mental Model — reason in this order

PRODUCT → CORRECTNESS → DATA/STATE → CONCURRENCY → SECURITY/PRIVACY → RELIABILITY → OBSERVABILITY → RECOVERY → PERFORMANCE/SCALE → OPERATIONS → MAINTAINABILITY → USER EXPERIENCE

Cross-cutting whenever they apply: idempotency · caching · async correctness · distributed-system behavior · time/date · money/precision.

UI correctness is never proof the system is production-ready. Compiling + unit tests + local dev = incomplete.

## Core Discipline

1. **Source of truth** — for every important fact name: authoritative source · derived state · cached state · transient UI state · sync mechanism. Two layers silently holding the same fact = future divergence bug. Ask: *where is this fact actually authoritative?*
2. **State machines** — lifecycle entities get explicit states, valid/invalid transitions, transition owner, side effects, failure behavior. Scattered status strings = future bug.
3. **Invariants** — list conditions that must always hold (unique allocation, authorized access, valid totals, no duplicate critical event, no impossible transition). Find the layer that owns each; that layer enforces it. App code alone is not enforcement — push to DB constraints where possible.
4. **Database integrity** — foreign keys, unique/check constraints, indexes, nullability, transactions/isolation, deletion/archival strategy. Safe migrations: add field → code supports both → backfill → switch → remove later. No irreversible migration without a recovery path.
5. **Concurrency** — for any shared or scarce resource ask: *what if two actors do this at once?* UI validation never solves races; the authoritative layer must reject conflicts. Actually run the two-simultaneous-requests test for every allocation (booking, inventory, payments, approvals).
6. **Idempotency** — anything retried or duplicated (payments, orders, reservations, record creation, webhooks, jobs, destructive actions) must not double-fire side effects. Repeated request = same outcome.
7. **Distributed thinking** — duplicate/delayed/missing/out-of-order messages, retries causing duplicates, timeouts, partial failures, eventual consistency. Never assume remote calls behave like local ones.
8. **Cache correctness** — classify: cache-safe (static catalog, prefs) / revalidate (live records, availability, money, permissions) / never-trust-cache (authority). Define TTL, invalidation-after-mutation (name every dependent view), stale behavior. Stale cache must never override authority.
9. **Async correctness** — stale closures, stale/out-of-order responses, cancellation, cleanup, duplicate listeners, reconnection, background tasks. Never sleep/setTimeout to hide a race.
10. **Client/browser correctness** — Back/Forward/refresh/deep-links/new tabs/logout/session expiry/multi-tab are application correctness. Navigation must never repeat side effects (resubmit payment, recreate appointment).
11. **Transactional consistency** — multi-record operations need a transaction, atomic write, or defined compensating action (saga/retry-safe op). No half-completed business process without a recovery path.
12. **Security** — authn, authz, least privilege, secrets (never committed, never in client bundles, never in logs, never in RAG/SOUL/skills), input validation at every trust boundary, file-upload safety, rate limiting on abuse-prone endpoints (login, reset, registration, messaging, uploads, expensive queries), dependency/supply-chain risk, security logging. **IDOR test:** swap every resource ID (routes, params, bodies, attachment URLs) and confirm denial. Frontend checks and hidden UI are not security boundaries.
13. **Privacy & auditability** — what data is collected, purpose, who reads it, retention/deletion/export, logging exposure. Minimize collection. Critical business/security actions get an audit trail (actor, action, resource, timestamp, before/after) without logging sensitive values.
14. **Money & time** — money: integer minor units or proper decimal, defined rounding/currency, no naive floats, immutable or auditable history, reconciled derived totals. Time: ONE storage-timezone policy, dates ≠ timestamps, test midnight/month/year boundaries and DST.
15. **Errors & failure isolation** — every substantial op has loading/success/empty/failure/retry/timeout/partial-failure states; failures never render as success; error messages help recovery. Localize failure (one component/dependency failing must not sink the system); degrade gracefully where a feature can survive a dependency outage. Never report success when the authoritative request failed.
16. **Observability** — *how would we know this broke in production? how would we find why?* Structured logs, error tracking, correlation IDs, health checks, actionable alerts (error rate, latency, auth failures, failed jobs, DB errors). Monitor what's actionable, not everything. SLI (measured) vs SLO (target) vs SLA (external commitment) — never invent SLAs without business context.
17. **Recovery & operations** — backups (DB + files, encrypted, independent storage) — a backup is not a recovery plan until restore is tested. Define RPO/RTO. Rollback strategy per deploy: app, DB, config, assets. Environment separation (no prod credentials for convenience). CI quality gates for important projects. Feature flags only when risk justifies: staged rollout + rapid disable path.
18. **Performance & scale** — measure before optimizing: latency, bundle size, N+1 queries, rendering cost, memory leaks. Ask *what breaks at 10x/100x/1000x data?* — indexes, pagination (cursor for large sets), query complexity, async jobs, connection limits. Neither blind optimization nor speculative over-engineering. Load-test critical paths before clients find the bottleneck.
19. **Production verification & readiness** — verify the DEPLOYED system: routes, auth, DB connectivity, integrations, storage, critical workflows, monitoring, rollback capability. For substantial systems run the readiness lens: correctness · security · reliability · recovery · observability · operations · performance · data · UX · maintainability. Data portability: controlled export (authorized, complete, auditable). Report only what actually ran: separate VERIFIED from NOT VERIFIED; paths with no device/credential/authority to test stay explicitly unverified — never narrated as passed.
20. **Incident response** — detect → assess → contain → recover → communicate → investigate → remediate → prevent recurrence. Preserve evidence; know notification paths for high-risk systems.

## Risk-Based Rigor

| Tier | Examples | Rigor |
|---|---|---|
| Low | copy, styling, spacing, typography | visual check |
| Medium | forms, navigation, client state, caching, API wiring | tests + manual flow walkthrough |
| High | auth, authz, payments, money/health/personal data, migrations, concurrency, destructive ops, prod infra | root-cause analysis, boundary + race tests, rollback plan, production verification, security review |

Scale effort to consequence × complexity. Don't run a production checklist on a typo fix; never ship a payment path on a styling workflow's verification.

## Root-Cause Rule

Symptom appears → (1) where did the incorrect state originate? (2) which layer owns the invariant? (3) why was it allowed to fail? (4) does the same bug class exist elsewhere? → fix the owning layer → add regression coverage → verify sibling flows. One guard in the shared path beats one guard per caller.

## Regression Order

changed feature → dependent features → related workflows → permission boundaries → failure behavior → regression suite → production where relevant.

## Authorship (standing user requirement)

Deliverable code must read as human-authored: idiomatic framework-standard structure (the ecosystem's own router, standard `pages/`/`components/` folders), no machine residue (dead exports, unused imports, scaffold comments). `references/style.md` = the authorship checklist plus split/move refactor verification pitfalls (leftover export lines, stale relative imports, smoke-with-console-capture after restructure).

Finding an issue is not the deliverable — fix it and re-run the affected suite before reporting.

## Generalized Lessons (validated on real projects)

- Client-side "slot available" checks don't prevent double allocation → scarce resources need authoritative conflict prevention at the persistence layer (constraint/transaction), plus a real race test.
- Mutation cache-invalidation must enumerate every dependent view (lists, calendars, dashboards, counts, notifications) — implicit invalidation leaves stale lies.
- Date filters computed in server-local timezone silently shift across deployments → define display timezone explicitly, test boundary dates.
- Stale async responses overwrite fresh state → sequence/cancel requests per view; never trust a response that arrives after the view moved on.
- Hidden UI controls are not access control → enforce per-resource authorization where the resource is served, and verify by manually altering identifiers.
- External payment flows (provider QR/hosted checkout): the provider's signed webhook + server-side status read are the ONLY authority — receipt screenshots and client claims never settle money. Verify webhook signatures (HMAC over raw body + timestamp), dedupe events through an event ledger (unique event id), verify amount before settling, and make settlement exactly-once (unique index on the payment link). The event ledger must distinguish RECEIVED from PROCESSED: only successful processing stamps the event processed; a transient failure returns 5xx and leaves it unprocessed so the provider's own retry re-runs the same event id (a racing legitimate delivery settling first counts as processed). The processed marker must be nullable with NO default — a NOT NULL DEFAULT now() auto-stamps every receipt and silently swallows retries. Reserve scarce slots at payment-initiation under a lock, and let late webhooks after a release record money without resurrecting a double-booked slot.
- Verified artifact ≠ intended source: CDN/cached builds serve stale assets after deploy (cache-bust production QA and check the deployed artifact), and inline deploy tools can ship content the repo file doesn't contain — write the file first, deploy FROM it, or you'll debug code that isn't running.
- Two creation paths for the same real-world entity (staff-entered record vs self-registration) → design claim-or-link AT CREATION plus a DB unique backstop; merge flows are recovery for legacy rows, not architecture.
- Rules configurable in an admin UI (hours, prices, categories) must drive every surface through ONE shared model; per-screen hardcoded values are latent divergence the first config change exposes.
- A capacity invariant enforced at only one call site (e.g. "at payment time") leaves sibling write paths free to double-book — enforce at the persistence layer for ALL writes; give the authoritative settle path an explicit bypass flag plus its own deterministic conflict policy (record the event, never resurrect a released slot). When capacity is per-resource (parallel chairs/dentists/rooms), scope EVERY conflict check — booking trigger, reserve-at-initiation, projection, settle — to the assigned resource; a global check left in one path rejects legal parallel work, and an unscoped settle approves same-resource double bookings. Auto-assigning a free resource must be serialized per partition (advisory lock inside the same trigger/transaction) — overlap constraints detect conflicts but cannot choose.
- Dev/demo tooling must be build-time stripped from production (env flag + dead-code elimination), proven by grepping the built bundle; QA must then exercise the production code path (e.g. provider-side settlement) instead of a dev crutch — crutch-dependent tests hide production bugs.
- Provider without idempotency keys: deterministic lookup/reuse BEFORE any provider POST, plus a DB twin-return path for concurrent first requests; document the ceiling.
- Test hygiene in shared databases: unique per-run identities/dates + cleanup; stray rows skew price-sorted/default pickers. Threshold-count assertions pass vacuously after UI granularity changes — assert artifact identity ("the booked patient's name appears"), not counts; likewise a readiness poll waiting on `count >= N` stops waiting the moment stale rows accumulate — poll for the specific row's identity (endpoint/id/key).
- Tests encode the invariant of the model they were written against. When the model changes (e.g. global → per-resource capacity), re-pin assertions to the new invariant before trusting any failure — same-resource conflict stays a conflict, parallel-across-resources becomes legal. Left unpinned, old tests fail correct new code and teach the wrong rule. Sweep fixture DATA in the same pass: rows legal under the old model (bookings outside working hours, on closed days, before enforcement existed) fail in ways that masquerade as product or provider bugs.
- Scheduling: PLANNED roster (per-resource day-of-week + working hours) determines future booking capacity; day-of presence/readiness is an operational override for warnings and ops views ONLY — it must never enable or block a booking (advance bookings cannot depend on who showed up today). A resource with no active roster row for a date is not a capacity unit that date; adding a resource expands capacity exactly when its roster is configured — nothing about resource counts is hardcoded. Opt-out presence rows expire with their date — never a permanent account property.
- Regression tests for retry/failure paths must manufacture the real failure (e.g. deliver the event before the provider state settles) instead of fabricating bad data; assert strict invariants (exactly one transaction/notification/row) while staying tolerant of WHICH legitimate delivery lands the effect — the provider's retries race your own. When a suite fails inside a batch, re-run it STANDALONE before condemning the product: test suites sharing one database interfere (a cleanup helper in run A deletes run B's fixture rows mid-test), so run suites sequentially and treat batch-only failures as interference until a solo run reproduces.
- `ADD COLUMN IF NOT EXISTS` is a no-op when the column pre-exists with different semantics — verify the actual default/nullability via information_schema after applying, especially for state flags (a NOT NULL DEFAULT now() 'processed'-style marker auto-stamps every row and silently defeats the state machine it was meant to support).
- When a new UI surface needs data a role's RLS rightly hides, do not widen the policy — expose a minimal SECURITY DEFINER function (ids/times/counts, no PII) to the role. Least privilege beats row-level relaxation.
- Any out-of-band state change a subagent makes on a live system (policy rewrite, data fix) must be reproduced as a versioned migration/config before accepting the work — otherwise reprovisioning silently reintroduces the bug it fixed.
- Correcting financial history is a controlled operation, never a silent UPDATE: edit (new value + mandatory reason) or Void (timestamped, excluded from totals), each writing an audit row with actor, role, before/after, reason.
- RLS policies are OR'd when permissive: one surviving `with check (true)` INSERT policy defeats every deny policy beside it, and policy names drift across migrations — when hardening a write path, drop every policy on the table by CATALOG DISCOVERY (loop pg_policies by table+cmd), then recreate exactly the intended set, and prove each role denial with a real forged-write probe (including the privileged roles). Verify with an actual insert attempt per role; inspecting the intended policies is not proof.
- An ALL policy bundles SELECT+INSERT+UPDATE+DELETE — splitting it into narrower verbs must explicitly recreate EVERY verb you still need. Missing SELECT breaks `INSERT … RETURNING` and reads while plain inserts still work; when a policy check that provably passes still reports "violates row-level security" on insert, test the insert WITHOUT a returning clause first — a vanished SELECT policy filters the returned row.
- Never recreate a function from memory: fetch the live signature and result type first (pg_get_function_arguments / pg_get_function_result) — a same-named helper may be a trigger function while the callable one has another name, and arity/return drift breaks every caller. Preserve exception message TEXT exactly when tests or clients match on it.
- A SECURITY DEFINER function is a write path of its own: denying client INSERT on the table does not stop forgery while the function stays EXECUTABLE by client roles (it bypasses RLS as the table owner). Revoke execute from public/anon/authenticated so only the definer functions and triggers that call it can run it — then re-grant EXPLICITLY to service_role (or the invoking definer's owner): `revoke … from public` also removes the implicit grant service_role depends on, and privileged paths die on their next call. Probe each role with an actual RPC call after changing grants.
- Object storage with CDN caching: an object GET can serve deleted or revoked bytes from cache until max-age expires — verify deletion via the delete response + authoritative list, never download-after; upload sensitive/private objects with cacheControl no-store so deletes and permission changes take effect immediately; a signed URL's TTL bounds exposure but is not revocation — test expiry with a short-TTL URL instead of waiting out production TTLs. Bucket-level size + MIME allowlists are the only real server-side upload validation boundary in managed storage (clients and filenames lie).
- Crash/kill recovery testing: model termination as abandoning the client mid-flow (no response handler, no unload hooks) and reopening with a fresh session — then assert the committed state is refetched and the retry cannot double-apply. Duplicate protection belongs in DB uniques and idempotent functions (identical-payload administrative retries, e.g. same-amount corrections, must be no-ops to protect audit integrity); if nothing persists at unload time, say so as the design rather than inventing an offline queue.
- Hardening a legacy multi-step call sequence: first PROBE which calls actually fail today (run the flow), then decide which errors become fatal. Legacy code routinely swallows a permanently-failing call — an RLS-denied delete may hard-error (`permission denied for table`) or silently affect 0 rows depending on GRANT vs policy — and the happy path has been shipping on that swallow. Making every error fatal converts a tolerated no-op into a broken happy path; treat known-permanent no-ops as explicitly best-effort (comment WHY) and fail only on steps whose failure changes real state. Compensation must undo only rows the flow owns.
- Credentials the system ISSUES (temp passwords, enrollment codes) must be crypto-random (CSPRNG over an unambiguous alphabet, 12+ chars), never derived from user-visible fields (names, emails, dates) — derivation makes them guessable by anyone who knows the person. Show the credential exactly once at handoff, never log or persist it plaintext.
- Documentation that names source locations (paths, symbols, line numbers) is executable truth: give it a runnable checker that verifies every referenced file/symbol/migration/test exists, and re-derive line references after ANY edit to the cited files — line numbers drift silently and review will not catch them. A checker that catches wrong names before ship beats a prose promise.
- Hardening/refactor passes run on a budget: classify findings P0 (security, data integrity, broken behavior, partial-state hazards) / P1 (maintainability that materially affects future changes) / P2 (cosmetic) — implement ALL P0, the P1s fixable without architectural risk, and P2 only when trivial and clearly beneficial. "10 meaningful fixes" beats 100 cosmetic changes; a smaller clean diff is a goal, not a shortfall. Deliver results by UPDATING the existing canonical release/audit document when one exists — a repo accumulating one REPORT file per pass is report noise, not documentation.

- Porting UI from a mock/demo data layer into a real schema: let DB defaults (uuid) fill ids — mock code ships fake string ids that break real columns — and check every mock column name against the live schema before wiring (a reserved-word name like `order` or a not-yet-existing column 400s silently with no UI symptom); the mock's simplified state machine also hides where invariants are enforced, so re-establish each preserved invariant at the destination's enforcement layer (trigger/RPC), not the UI happy path.
- Provisioning a user through a shared client's `signUp` switches that client's active session, so follow-up role/profile writes run as the wrong principal and fail RLS — run each provisioning step on its own client instance.
