# Dependency security remediation

When `hermes security audit` reports known vulnerabilities in Hermes's own Python dependency graph, clear them at the dependency source of truth (`pyproject.toml` + `uv.lock`), never by spot-editing one installed venv. Three states must agree before the finding count is real: the source pins, the resolved lock, and the installed `*.dist-info/METADATA` that `uv pip check` validates.

## Procedure

1. **Read the real finding set.** `hermes security audit --json --skip-mcp` yields `finding_count` plus per-finding `package`, `version`, `severity`, `fixed_versions`. The audit scans the **selected runtime venv** (resolved through `pm.environments.selected_venv`), not the host interpreter — read installed versions from that venv's own site-packages, because a parent generation's `PYTHONPATH` can shadow a fresh generation and make two versions of one package visible at once. Isolate the probe: run that venv's own python with `-S`, drop `PYTHONPATH` from the child env, and enumerate with `importlib.metadata.distributions(path=[site])` (then dedupe by normalized package name) — a bare `distributions()` walks the whole inherited `sys.path`, so a stale generation's `*.dist-info` on `PYTHONPATH` inflates the finding count with versions the selected venv does not run.
2. **Take the `fixed_versions` floor for each package and confirm it is resolvable.** The project's release-age policy (`exclude-newer` under `[tool.uv]` in `pyproject.toml`) exists to quarantine brand-new packages — exactly where security fixes land. If the fix is filtered out, `hermes pm lock` will silently not move to it; say so rather than forcing an unpinned resolution. Distinguish "cannot resolve because filtered by age" from "cannot resolve because conflicted": the remedies differ (age-in vs override).
3. **Bump the exact pin** in `pyproject.toml` `dependencies`. Keep the project's exact-pin policy; do not introduce ranges. Run `hermes pm lock` and confirm it resolves to the fixed version.
4. **Break a vendored stale pin with `[tool.uv] override-dependencies`.** If resolution fails because a package pins the exact old version (e.g. `browser-harness` pins `pillow==12.3.0`), add the target to `override-dependencies` — uv replaces the stale requirement so the resolver accepts the patched wheel. Remove the override when upstream lifts its own pin.
5. **Relax the installed metadata pin so `uv pip check` agrees.** The override fixes RESOLUTION only; `uv pip check` reads the literal `Requires-Dist` in the installed dist-info and still rejects it. Rewrite `pkg==X` to `pkg>=X` in the selected venv's `*.dist-info/METADATA`, keeping any environment marker after the `;`. Keep this as a small re-runnable script and invoke it after **every** dependency re-sync — `hermes pm install`/relock mints a NEW venv generation and restores the vendor pin. Wire the invocation into the same cron entry point that re-applies local source patches (e.g. `ensure_patches.py`).
6. **Verify to green before claiming done:** `hermes security audit --json --skip-mcp` reaches the expected `finding_count` floor (0 for a fully-patched graph), `uv pip check` on the selected venv reports "All installed packages are compatible", and the repo's targeted regression tests pass.

## Pitfalls

- **An audit that scans X must fail closed when X is unreachable — never fall back to scanning Y.** A silent host-interpreter fallback reports the host's packages as the runtime's and produces a finding set you cannot fix at the source. (mechanism: `importlib.metadata.distributions()` reads the calling process's own `sys.path`.)
- **`override-dependencies` and `uv pip check` are independent gates.** Clearing one never clears the other: resolution accepts the patched wheel while validation still rejects the literal metadata pin.
- **Do pin work in `pyproject.toml`, not in one venv.** Every `hermes pm install`/relock mints a fresh generation and re-selects it, so manual pin surgery in the old generation is dead on arrival.
- **Check `exclude-newer` before assuming a bump resolves.** A just-published security fix is the canonical case the age filter blocks.
- **Read versions from the selected venv's site-packages, not the ambient process.** Parent-generation `PYTHONPATH` entries shadow a fresh generation and make a manual probe read the wrong (older) package set.
