# Live database access when the MCP is permission-denied

Project-scoped MCP calls (`apply_migration`, `execute_sql`, `list_migrations`, `get_project`) can return `MCP error -32600: You do not have permission` while the same project is fully manageable from the owner's logged-in dashboard. Before any fallback, determine whether the MCP account can see the project at all: call `list_projects`. Zero visible projects (or this project missing) means the connection is authed to a different/empty Supabase account — re-authenticating the connection (its OAuth connect flow — drivable agent-side via the ClawLink connect tool, which auto-completes in the existing browser session) restores the entire project-scoped MCP path in one step and is far cheaper than either fallback below. Only when the account is correct and the project is genuinely permission-walled: do not loop the MCP — switch to one of these two verified paths.

## Credential → capability matrix (what each key can actually reach)

Before concluding a Supabase capability is "blocked", match the credential to the operation. Different keys reach different planes and the wrong key produces a misleading error:

| Credential | PostgREST rows (DML) | DDL (create/alter) | Auth admin `/auth/v1/admin/users` | Management API (projects, SQL run) |
|---|---|---|---|---|
| `sb_secret_` service key | yes (bypasses RLS) | **no** | yes (create/list/delete users) | **no** — `401 "JWT could not be decoded"` |
| `sb_publishable_` / `anon` key | yes (RLS applies) | no | no | no |
| Personal Access Token (PAT) | no | via the `pg`/SQL endpoint | no | yes |
| MCP `execute_sql`/`apply_migration` | — | yes **only if** the authed account owns the project | — | — |

Pitfall: the Management API rejecting the service key with `401 "JWT could not be decoded"` is NOT a bad/rotated key — that endpoint accepts only a **Personal Access Token** (dashboard → Account → Access Tokens). Don't read it as "the service key is wrong" and go hunting for a different secret; you are holding the wrong *kind* of credential for that plane.

Pitfall: `execute_sql`/`apply_migration` returning "You do not have permission" means the MCP is authed to a *different Supabase account* than the project owner, not that the project is unreachable. The diagnostic probe is `list_projects`: an account that sees ZERO projects is the different-account case (re-auth fixes it outright), while an account that sees the project but not its data is the genuine permission-walled case where the fallbacks below apply. The same project is often fully workable through the service key (PostgREST + Auth) even when the MCP is useless. Probe the data plane before declaring the project blocked — and never build the dashboard-automation fallback before the account-identity probe and a re-auth attempt.

**Key model + length trap (the "Invalid API key" that is not a bad key).** A project exposes BOTH a legacy `anon`/`service_role` JWT (~208/219 chars, `eyJ…`) and a new-style `sb_publishable_`/`sb_secret_` key (~46/41 chars). Either anon flavor (the `anon` JWT or the `sb_publishable_` key) is valid as the client anon key — a bundle showing one or the other is fine. But a key pasted from chat or a dashboard can carry extra trailing characters and return `401 Invalid API key` even though it looks correct; this reads like a bad/rotated credential and sends you hunting for a different secret when the value is just wrong. Before wiring a client key, confirm its exact value and length against the authoritative source — `GET /v1/projects/{ref}/api-keys` with the PAT returns the real key list — and diff what you are about to deploy against it. Never trust a length you computed from a pasted string.

Pitfall: the service key bypasses RLS but NOT trigger-level guards. A `P0001` error carrying a domain message (e.g. `availability is clinic-managed (owner)`) on a service-key write means a trigger enforces a caller-ROLE contract and the service JWT is simply the wrong actor. Act as the owning role instead of hunting for a bypass: password-grant the actor (`POST {url}/auth/v1/token?grant_type=password`, apikey = the anon/publishable key, body `{"email","password"}`) and retry the write with that user's access token. Never drop or weaken the guard to push an ops write through.

## Real auth works before any DDL (an empty schema does not block auth)

Supabase Auth stores users in `auth.users`, which Supabase manages — it is NOT in your `public` schema and needs no migration. So even when DDL is blocked and the app schema is empty, you can create/verify/delete real auth users through `/auth/v1/admin/users` with the service key (200 + a real UUID on create). Consequence: "make auth real" is often achievable *before* the persistence tables exist — real registration/login/session is a Supabase-managed capability independent of your `public.*` tables. What missing DDL blocks is app-level data (profiles, wishlist, RLS on your own tables), not authentication itself.

This splits "real auth" into two independently-verifiable halves:

- **Authn (sign-in, session, logout):** real via Supabase Auth, no DDL needed. The frontend only needs `VITE_SUPABASE_URL` + the publishable key set. With those absent it silently falls back to a localStorage demo mode — so grep the deployed bundle for the project ref before claiming auth is live (the ref's absence = still demo, even though the auth code exists).
- **Authz + user data (RLS, profiles, roles):** needs the `public` schema, hence DDL. When DDL is blocked, report these as *unapplied* and never describe an unapplied migration as deployed.

## Path 1: dashboard SQL Editor via desktop automation (DDL and writes)

1. Open `https://supabase.com/dashboard/project/<ref>/sql/new` in the user's logged-in browser (computer-use: ctrl+l → type URL → return; capture and confirm the SQL Editor before touching it). Target the window by `pid` + `window_id` from `list_windows` — `app=` alone can route to the wrong tab, and input actions refuse with "No active window — call capture() first" until that exact window has been captured.
2. Put the SQL on the clipboard from the terminal: `xclip -selection clipboard < file.sql`. The Monaco editor accepts full-file pastes (18 KB verified). Never type SQL through xdotool — it mangles quotes and is slow.
3. Click the editor body, paste, and run keyboard-first in one shot: `xdotool windowactivate <id>; mousemove <x> <y> click 1; key ctrl+a; key ctrl+v; key ctrl+Return`. The `ctrl+a` matters: without it the paste appends to whatever SQL the editor already holds, and a stale half-query runs instead of yours. Note `ctrl+Return` submits only the highlighted selection (the toolbar button reads "Run selected"), so after a paste the text may still be selected and a stray selection runs a subset — make sure the whole intended batch is what will execute. The run key is `ctrl+Return` (the keysym is `Return`; `xdotool key ctrl+enter` silently ignores `enter` and does nothing). Prefer this over clicking Run. When unsure the paste landed, verify before running: `ctrl+a`, `ctrl+c`, then diff the clipboard against the source file — a click that misses the Monaco body leaves the editor empty (or holding a stale query) and the run executes the wrong SQL while still reporting Success. If `computer_use` background input refuses ("no focus-free input backend") or its window tracking goes stale, drop to raw xdotool: rediscover the browser window (`xdotool search --class <browser>` + `getwindowname`, then `windowactivate <id>`) and use absolute screen coordinates (the same space as the PNG→native calibration in the pitfall below). `xdotool`/`xclip` require an X display — if the terminal throws `Can't open display: (null)`, run `export DISPLAY=:0` first (find the live display via `ls /tmp/.X11-unix/` → `X0` means `:0`; confirm with `xdpyinfo`).
4. DDL or drop statements trigger a "Potential issue detected" modal with **Cancel** / **Run query** — this is the dashboard's generic destructive-ops warning and appears even for idempotent `drop ... if exists` migrations. **Run query** is the expected action for an authorized migration. Prefer avoiding the modal when you can: `create table` / `create index` / `create policy` do NOT trigger it, while `drop` and `revoke` do — on a brand-new table, `drop policy if exists` and `revoke` are no-ops, so drop them from the batch to run without the confirm click at all.
5. Verify in the Results panel, then read back the effect (Path 2 or a `select` in the same editor). An error in the Results panel is a real database error, not a transport failure — fix the SQL's dependencies, not the delivery.

Pitfall: `computer_use`'s `coordinate=` is native desktop space, but vision screenshots are rescaled — and the reported `bounds_scale` is approximate enough to make a button click miss entirely. Vision estimates of a modal button's position miss by ~±20px. Click the one button that must land (destructive-modal **Run query**) deterministically instead: detect its exact pixel centroid in the capture PNG with a PIL color mask (that button is amber/yellow: `r>190 and 150<g<225 and b<130`; scan only the modal band — the browser's amber tab favicons at the top also match), then convert PNG→native with uniform scale: `native_x = window_x + png_cx × (win_w / png_w)`, `native_y = window_y + png_cy × (win_h / png_h)` (window geometry from `xdotool getwindowgeometry <id>`). That lands the click on the first try. A missed click looks like "the query didn't execute" when it was never submitted — read the Results panel state before assuming a SQL error or retrying.

## Path 2: PostgREST probes using the repo's own frontend env

The app's frontend env (e.g. `frontend/.env.local`: `VITE_SUPABASE_URL` + `SB_SECRET`/publishable key) authenticates plain PostgREST requests against the live project. Use it to read rows before/after a change and to confirm a migration landed — the fastest verification layer, no MCP needed. Load key values inside a script; never print them. A PostgREST 404 on a table name means the table does not exist (or is not exposed), which doubles as a cheap schema-existence probe. The converse needs care: a 200 read with the `SB_SECRET`/service-role key proves the table exists but bypasses RLS, so it is NOT proof a policy landed — for that, trust the SQL Editor's success on the `create policy` statement or query `pg_policies`. The same key reaches Supabase Auth's admin REST surface (`/auth/v1/admin/users`) for a read-only auth-user inventory — the way to cross-check auth users against `profiles` rows when auditing identity consistency. Never echo the key or dump user PII into reports. Config/secret tables often use a generic kv schema (`key`, `value` rows) where live secret material sits in innocuously named `value` columns — `select *` streams those secrets into tool output, and a redaction filter keyed on column NAMES (`key`/`secret` in the column name) misses them entirely. Select only the columns you need (e.g. one config row's `value` for a mode flag) and redact by value PATTERN (`sk_`, `pk_`, `whsk_`, `sbp_`, `eyJ`); any secret that already surfaced into output counts as exposed and warrants rotation.

A PostgREST `DELETE` returns 204 whether or not its filter matched any row — the status proves the request was accepted, not that anything was removed. Verify every deletion by requerying a discriminating predicate (a status/flag/category column), never by the 204 alone and never by refetching the deleted id (an empty result is ambiguous between "deleted" and "never existed"). The same trap applies to filtered updates: confirm by the changed column's new value, not by the response code.

## Migration-vs-live-DB drift (the trap behind "my migration fails on a table that exists")

A repo migration chain only replays what the live database actually has. Before running migration N against a long-lived project, probe the objects it references; SQL `42P01: relation ... does not exist` or a PostgREST 404 means an earlier migration in the chain never applied live (live schema drifted from the repo). Fix by applying the missing earlier migration first (or creating just the missing object, with its RLS and grants, from that earlier file) — never patch around the missing dependency inside the consumer migration.

Pitfall: connecting Supabase to a GitHub repo does NOT auto-apply `supabase/migrations/`. Migrations land only via CLI, `apply_migration`, or the SQL Editor. Pushing a migration file is not applying it; verify with a live probe of the object the migration creates.

Confirm a migration landed by probing the objects it changes — columns via `information_schema.columns`, table existence, and redefined function signatures via `pg_get_function_identity_arguments(p.oid)` joined through `pg_namespace` — never by trusting a clean run. Always qualify the OID (`p.oid`): a bare `oid` in that join is ambiguous (42702) and its "0 rows" error reads like the functions are missing.

## Verifying a SECURITY DEFINER guard change conclusively

Adding an authorization guard to a live function is the highest-stakes kind of migration — an error makes the function unusable, a silent miss leaves the hole open. Verify it in three layers:

1. **Transcribe + diff before applying.** When rewriting a live function to add a guard, transcribe the original body exactly and diff your new body against it — the ONLY delta should be the guard block. A byte-exact diff proves the transcription did not drift (a silently altered condition is invisible in a later "Success" run and can turn a reject into an allow).
2. **Prove the guard is in the live catalog.** After applying, query `pg_proc` for the guard's literal token (e.g. `select count(*) from pg_proc where prosrc like '%not authorized to complete this appointment%'`) — a clean SQL-Editor run is not proof the right function body landed, especially when overloads exist. `create or replace` only replaces the MATCHING signature; a stale overload of the same name (a 4-arg sibling from an older migration) survives as a second unguarded entry point. Detect it with `select oid::regprocedure from pg_proc where proname='<fn>'` (more than one row = a latent hole + `42725 ... is not unique` on any bare call whose args fit both), then `drop function if exists public.<fn>(<exact stale args>)` so only the guarded form remains.
3. **Make the behavioral test conclusive (the SQL Editor does not surface `RAISE NOTICE`).** A DO-block test that raises `PASS:`/`FAIL:`/`SKIP:` notices and returns cleanly shows "Success. No rows returned" for BOTH a pass and a skip — the Results panel cannot tell them apart. So let ONLY the expected behavior return normally ("Success"), and `raise exception` a *distinct* message for every other outcome: missing fixture → `raise exception 'NO_FIXTURE'`; the bug still present → `raise exception 'FAIL: <what should have been blocked>'`. Then "Success" unambiguously means the guard held, and any fixture gap or real hole surfaces as a readable error instead of being masked as success. A behavioral guard test must actually CHANGE the value it targets. Guards keyed on `IS DISTINCT FROM` (or any change check) do not fire when the mutation writes the value already present — a test that PATCHes `payment_status` to the value it already has, or `final_fee` to the same number, is a no-op and reads as "not blocked", masking a working guard (this produced a false "fix didn't apply" once). Use a novel value each run (e.g. a random amount, the opposite status). Wrap the test in an explicit transaction and `rollback` (or run it against state you can restore) so a FAIL case does not leave a completed write behind.

To run that test as a *specific* actor (the caller the guard must reject), emulate their JWT before calling the function:
`select set_config('request.jwt.claims', (select json_build_object('sub', u.id, 'email', u.email, 'role','authenticated')::text from auth.users u join <entity> e on lower(e.email)=lower(u.email) where e.role='<role>' and e.active limit 1), true);`
`auth.uid()` and `auth.email()` read these claims, so the SECURITY DEFINER function then sees the emulated caller. Resolve the actor's `sub`/`email` from `auth.users` (the identity table) — `profiles` usually has NO `email` column (42702), so joining `profiles.email` is the wrong lookup. `set_config(..., true)` is transaction-local, so the enclosing `rollback` restores the real caller. Pick a target row the emulated actor must NOT be able to reach and assert the reject.
